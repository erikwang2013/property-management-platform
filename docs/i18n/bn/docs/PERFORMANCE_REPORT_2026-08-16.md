### উপসংহার

- সব ইন্টারফেস ২০ VU-তে ০ ব্যর্থতা, p95 < 220ms, স্বাস্থ্যকর।
- **থ্রুপুট বাধা প্রায় 230–250 rps**: ২০ VU → ৫০ VU-তে থ্রুপুট বাড়ে না বরং সমতল থাকে (dashboard 227.9 → 226.9, fee 197 → 247), অথচ p95 লেটেন্সি দ্বিগুণ (~190ms → ~540ms)। সিঙ্গেল মেশিনে ৩২ worker-এ প্রতি worker প্রায় ৭–৮ rps, এটি PHP সম্পূর্ণ চেইনের (MySQL কোয়েরি, Redis ক্যাশে রাউন্ডট্রিপ সহ) সিঙ্গেল-কোর প্রসেসিং সীমার বৈশিষ্ট্য, সংযোগ নিঃশেষ নয় (কোনো ব্যর্থ রিকোয়েস্ট নেই)।
- সুপারিশ: সিঙ্গেল মেশিনে এই স্কেল যথেষ্ট (প্রায় ২ কোটি রিকোয়েস্ট/দিন); উচ্চতর থ্রুপুট চাইলে প্রথমে অনুভূমিকভাবে ইনস্ট্যান্স বাড়ান, তারপর প্রতিটি ইন্টারফেসের SQL ও ক্যাশে হিট রেট পরীক্ষা করুন (নিচে দেখুন)।

## 3. স্লো কোয়েরি পর্যালোচনা

- ফি টেবিল `management_fee_bill` / `management_fee_payment`-এর ইনডেক্স সম্পূর্ণ (paid_at, bill_id, owner_id, payment_number ইত্যাদি), কোর কোয়েরিগুলোর জন্য ইনডেক্স আছে।
- আবিষ্কার: ফি তালিকা `payment_number like %kw%` ফাজি সার্চ (লিডিং ওয়াইল্ডকার্ড), ইনডেক্স ব্যবহার করা যায় না, ডেটা বড় হলে এই শর্ত ফুল টেবিল স্ক্যানে পরিণত হয়। এটি কম-ফ্রিকোয়েন্সি অ্যাডমিন সার্চ, আপাতত মোকাবেলা করা হয় না; ডেটা বাড়লে ইনভার্টেড বা প্রিফিক্স ইনডেক্সে পরিবর্তন করা যেতে পারে।
- **MySQL slow_query_log OFF অবস্থায় আছে**: চালু করার এবং `long_query_time=1` সেট করার সুপারিশ, আসল স্লো SQL পর্যবেক্ষণ করুন (লোড টেস্ট থেকে অনুমান নয়)। প্রোডাকশনে চালান:
  ```sql
  SET GLOBAL slow_query_log = ON;
  SET GLOBAL long_query_time = 1;
  ```
- ড্যাশবোর্ড এগ্রিগেশন: প্রতিবার ক্যাশে পুনর্নির্মাণে প্রায় ৮টি COUNT এগ্রিগেশন + ৩০ দিনের গ্রুপ পরিসংখ্যান, একবার পুনর্নির্মাণ সেকেন্ড-স্তরের খরচ, Redis ৫ মিনিট ক্যাশে শোষণ করে (নিচে দেখুন), হট পাথ নয়।

## 4. Redis ক্যাশে পুনঃপরীক্ষা

- ড্যাশবোর্ড ক্যাশে `dashboard:data`: `setex 300`, হিট হলে ~10ms, মিস হলে পুনর্নির্মাণ সেকেন্ড-স্তরের। **সমস্যা: কোনো রাইট অপারেশনে ইনভ্যালিডেশন লজিক নেই**, ডেটা পরিবর্তনের পর সর্বোচ্চ ৫ মিনিট পুরনো থাকে। ফি/সম্পত্তি রাইট ইন্টারফেসে এই key মুছে দেওয়ার সুপারিশ (এক লাইন `del dashboard:data`)।
- **ক্যাশে ব্রেকডাউন সুরক্ষা নেই**: key মেয়াদ শেষ হওয়ার মুহূর্তে ৩২টি worker একসাথে পুনর্নির্মাণ করে (৮টি এগ্রিগেশন কোয়েরি বারবার চালায়)। ডেটা বড় হলে সাধারণ মিউটেক্স যোগ করার সুপারিশ (যেমন `set nx ex` লক + ডাবল-চেক)।
- অনুমতি ক্যাশে `perm:{adminId}` 60s, আচরণ স্বাভাবিক।
- অবশিষ্ট তদন্তের আইটেম: লোকাল Redis-এ `dashboard:data` key কখনো দেখা যায়নি (একাধিক db-তেও নেই), কিন্তু ইন্টারফেস রেসপন্স স্বাভাবিক এবং হিট হলে লেটেন্সি স্পষ্টত কম। লোড টেস্টের সময় মাঝে মাঝে 403 "অনুমতি ছাড়া অ্যাক্সেস" (২ বার দেখা গেছে পরে স্থিতিশীল ২০০)। সন্দেহ লোকাল মেশিনে একাধিক Redis ইনস্ট্যান্স/এনভায়রনমেন্ট ভেরিয়েবল কনফিগারেশন অনলাইন থেকে আলাদা, টার্গেট পরিবেশে পুনঃযাচাই প্রয়োজন; লোড টেস্টের উপসংহারে প্রভাব নেই (স্থিতিশীল অংশে ০ ব্যর্থতা)।
