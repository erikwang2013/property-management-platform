## 1. বর্তমান অবস্থা জরিপ

### 1.1 টেবিল কাঠামো শ্রেণিবিভাগ (৬৫টি টেবিল, docs/install.sql দিয়ে যাচাই)

| শ্রেণি | টেবিল | ব্যাখ্যা |
|------|-----|------|
| গ্লোবাল/প্ল্যাটফর্ম টেবিল | management_admin_user / admin_role / admin_permission / admin_user_role / admin_role_permission, management_system_config, management_operation_log | অথরাইজেশন, কনফিগ, অডিট, স্বাভাবিকভাবেই প্ল্যাটফর্ম-স্তরের, টেন্যান্টের সাথে যুক্ত নয় |

### 1.2 অথরাইজেশন চেইন (admin পাশ, কোড দিয়ে যাচাই)

```
গ্লোবাল মিডলওয়্যার: Cors → SecurityFilter → RateLimit
রুট গ্রুপ মিডলওয়্যার: AdminAuth(JWT → $request->adminId) → AdminPermission(RBAC method.path) → OperationLog → Controller
```

- `AdminAuth` ইতিমধ্যে request ইনজেকশন প্যাটার্ন তৈরি করেছে (`$request->adminId`), টেন্যান্ট কনটেক্সট সম্পূর্ণভাবে কপি করা যায়
- `AdminPermission` প্ল্যাটফর্ম-স্তরের RBAC, টেন্যান্ট আইসোলেশনের সাথে **অর্থোগোনাল**, স্তরে স্তরে যুক্ত করা যায়
- service মালিক পাশ: JWT-তে owner_id থাকে, ডেটা room_owner → room.community_id দিয়ে স্বাভাবিকভাবে সীমিত, ক্রস-টেন্যান্ট ঝুঁকি কম

### 1.3 মূল উপসংহার

- কোনো তৈরি SaaS টেন্যান্ট মডেল নেই; `management_tenant` নাম ভাড়াটে দখল করেছে, নতুন কনসেপ্টের নাম এড়িয়ে চলতে হবে
- সব কন্ট্রোলার সরাসরি Eloquent কোয়েরি করে, repository স্তর নেই, গ্লোবাল স্কোপ নেই —— আইসোলেশন রিফ্যাক্টর মডেল স্তরে করতে হবে
- config/database.php সিঙ্গেল কানেকশন, তবে illuminate/database নেটিভভাবে মাল্টিপল connection সমর্থন করে (আলাদা ডেটাবেস বিবর্তনের জন্য রিজার্ভ)

## 2. সমাধান তুলনা ও সুপারিশ

| সমাধান | মেকানিজম | রিফ্যাক্টরের পরিমাণ | অপারেশন খরচ | প্রযোজ্য |
|------|------|--------|----------|------|
| **A. শেয়ার্ড ডেটাবেস + tenant_id সারি আইসোলেশন (সুপারিশকৃত)** | টেন্যান্ট টেবিল + বিজনেস টেবিলে tenant_id কলাম + Eloquent গ্লোবাল স্কোপ ফিল্টার | মাঝারি (২ টেবিলে কলাম যোগ + মিডলওয়্যার + গ্লোবাল স্কোপ + বিদ্যমান ডেটা ব্যাকফিল) | কম (সিঙ্গেল ডেটাবেস ব্যাকআপ/মাইগ্রেশন অপরিবর্তিত) | ছোট-মাঝারি সম্পত্তি, একক টেন্যান্ট <৫০ লাখ সারি |
| B. আলাদা ডেটাবেস (প্রতি টেন্যান্ট এক ডেটাবেস) | কানেকশন রাউটিং + ক্রস-ডেটাবেস এগ্রিগেশন | উচ্চ (কানেকশন ম্যানেজমেন্ট/ক্রস-ডেটাবেস রিপোর্ট/মাইগ্রেশন×N/ব্যাকআপ×N) | উচ্চ | বড় গ্রুপ, কমপ্লায়েন্স আইসোলেশন প্রয়োজন |
| C. হাইব্রিড (সংবেদনশীল ডেটাবেস আলাদা + শেয়ার্ড) | A+B কম্বিনেশন | উচ্চ | উচ্চ | পেমেন্ট/ফেসিয়াল ইত্যাদি শক্তিশালী আইসোলেশন দৃশ্য |

**সুপারিশ A, B বিবর্তনের দিক।** কারণ:

1. বর্তমান ৬৫টি টেবিল একক ডেটাবেসে, A-এর tenant_id ডেটা মডেল ভবিষ্যতে ডেটাবেস ভাগ করাকে বাধা দেয় না (ফিল্টার গ্র্যানুলারিটি সারি থেকে ডেটাবেসে পরিবর্তন হলেই হয়, A সমাধানে টেন্যান্ট ID ইতিমধ্যে গ্লোবালি মডেল করা)
2. বিজনেস ডেটা সব community_id দিয়ে অন্তর্গত, tenant_id শুধু **টপ-লেভেল টেবিলে** যোগ করতে হবে, মাঝের ৪০টি বিজনেস টেবিল অ্যাক্সেস পাথ দিয়ে নিশ্চিত হয়, প্রতি টেবিলে কলাম যোগ এড়ানো যায়
3. দুই পাশ (admin/service) একই ডেটা মডেল শেয়ার করে, A-এর রিফ্যাক্টর admin পাশের রানটাইম স্তরে কেন্দ্রীভূত
4. সিঙ্গেল মেশিন ডিপ্লয়মেন্টের বর্তমান অবস্থায় B-এর ব্যাকআপ/মাইগ্রেশন জটিলতা অসহনীয়

## 3. আইসোলেশন পয়েন্ট ডিজাইন

### 3.1 ডেটা মডেল (ন্যূনতম সেট)

- নতুন `management_platform_tenant` তৈরি করুন (ভাড়াটে টেবিল management_tenant-এর সাথে সংঘর্ষ এড়াতে): id/name/status/created_at ইত্যাদি
- `management_community`-তে `tenant_id BIGINT NOT NULL DEFAULT 0` যোগ, ইনডেক্স `(tenant_id, community_id)`
- `management_admin_user`-তে `tenant_id BIGINT NOT NULL DEFAULT 0` যোগ (0 = প্ল্যাটফর্ম সুপার অ্যাডমিন)
- বিজনেস মাঝের টেবিলে (building/room/fee_bill ইত্যাদি ৪০টি) **কলাম যোগ করা হবে না**, community_id দিয়ে অন্তর্গত

### 3.2 রানটাইম স্তরের তিনটি জিনিস

1. **TenantContext মিডলওয়্যার**: JWT payload-তে `tenant_id` ক্লেইম যোগ → `$request->tenantId` (AdminAuth ইনজেকশন প্যাটার্ন কপি); লগইন/ইনস্টল/প্ল্যাটফর্ম-স্তরের রুট (user/role/permission/config) পাস লিস্ট
2. **TenantScope গ্লোবাল স্কোপ**: Community ও প্ল্যাটফর্ম-স্তরের বিজনেস মডেলে Eloquent গ্লোবাল স্কোপ লাগান, `$request->tenantId` অনুযায়ী স্বয়ংক্রিয় ফিল্টার; `find()`-ও স্কোপের অধীনে, স্বাভাবিকভাবে ক্রস-টেন্যান্ট একক সরাসরি কোয়েরি প্রতিরোধ
3. **Tenant::for() এক্সপ্লিসিট কনটেক্সট**: শিডিউলড টাস্ক/কিউ/ইমপোর্টে HTTP রিকোয়েস্ট নেই, ক্লোজার দিয়ে এক্সপ্লিসিট টেন্যান্ট নির্ধারণ; কনটেক্সট অনুপস্থিত থাকলে **fail-closed** (কোয়েরি অস্বীকার), ফিল্টার ছাড়া নীরবে ছাড় দেওয়া নিষিদ্ধ

### 3.3 অননুমোদিত অ্যাক্সেস সুরক্ষা পরীক্ষার পয়েন্ট (অ্যাকসেপ্টেন্স ম্যাট্রিক্স)

| টেস্ট কেস | প্রত্যাশিত |
|------|------|
| টেন্যান্ট A অ্যাডমিন টেন্যান্ট B-এর community/building/fee_bill তালিকা দেখে | খালি বা শুধু A-এর ডেটা ফিরবে |
| টেন্যান্ট A অ্যাডমিন টেন্যান্ট B-এর একক রেকর্ড find/update/delete (সরাসরি id) | 403 / খালি ডেটা / অস্বীকার |
| প্ল্যাটফর্ম অ্যাডমিন (tenant_id=0) ক্রস-টেন্যান্ট অপারেশন | ছাড় (প্ল্যাটফর্ম-স্তরের ক্ষমতা) |
| service মালিক ক্রস-কমিউনিটি অপারেশন (ফি পরিশোধ/মেরামত) | অস্বীকার (community অন্তর্গত যাচাই) |
| শিডিউলড টাস্ক/কিউ টেন্যান্ট কনটেক্সট নির্দিষ্ট না করে | fail-closed এরে, ফিল্টারহীন নয় |

## 4. বিবর্তনের পথ (ধাপে ধাপে মাইগ্রেশন)

| ধাপ | বিষয়বস্তু | অ্যাকসেপ্টেন্স |
|------|------|------|
| 1. ডেটা স্তর | platform_tenant টেবিল তৈরি + community/admin_user-এ কলাম যোগ + ইডেমপোটেন্ট মাইগ্রেশন + ডিফল্ট টেন্যান্ট ইনিশিয়ালাইজ ও বিদ্যমান ডেটা ব্যাকফিল | প্রতি কমিউনিটিতে টেন্যান্ট বাধ্যতামূলক, অরফান ডেটা রিপোর্ট শূন্য |
| 2. রানটাইম স্তর | TenantContext মিডলওয়্যার + TenantScope + Tenant::for() টুল + রুট পাস লিস্ট | সিঙ্গেল-টেন্যান্ট রিগ্রেশন: সম্পূর্ণ ১৩৩টি টেস্ট পাস |
| 3. পাইলট মডিউল | গ্রুপ ম্যানেজমেন্ট → কমিউনিটি → মালিক → ফি (বিল) এই চারটি মডিউল প্রথমে আইসোলেশন চালু | অননুমোদিত অ্যাক্সেস টেস্ট ম্যাট্রিক্স পাস |
| 4. সম্পূর্ণ বিস্তার | ব্যাচ অনুযায়ী (১ম ব্যাচ কোর → ২য় ব্যাচ সহায়ক → এক্সটেনশন মডিউল) মডিউল-প্রতি আইসোলেশন চালু | সব মডিউলের অননুমোদিত অ্যাক্সেস ম্যাট্রিক্স পাস |
| 5. বিবর্তন | সিঙ্গেল টেন্যান্ট ডেটা >৫০ লাখ সারি বা কমপ্লায়েন্স প্রয়োজন হলে ডেটাবেস ভাগ মূল্যায়ন (B সমাধান), A-এর ডেটা মডেল বাধা দেয় না | ডেটাবেস ভাগ সমাধান পর্যালোচনা |

ডেটা মাইগ্রেশন কৌশল: বিদ্যমান ডেটা সব "ডিফল্ট টেন্যান্ট"-এ রাখা হয় (মাইগ্রেশন স্ক্রিপ্ট তৈরি করে), ব্যবসার ডেটা মুছে বা বদলানো হয় না; মাইগ্রেশন স্ক্রিপ্ট ইডেমপোটেন্ট, বারবার চালানো যায়।

| গ্লোবাল স্কোপ প্ল্যাটফর্ম-স্তরের কোয়েরি ভুলভাবে আঘাত করে (ড্যাশবোর্ড ক্রস-জোন সামারি) | ড্যাশবোর্ড/রিপোর্ট | প্ল্যাটফর্ম-স্তরের ইন্টারফেসে এক্সপ্লিসিট Tenant::without() বা tenant_id=0 বাইপাস |
| শিডিউলড টাস্ক/কিউতে রিকোয়েস্ট কনটেক্সট নেই | আদায়/SLA/নোটিফিকেশন ইত্যাদি ব্যাকগ্রাউন্ড টাস্ক | Tenant::for() এক্সপ্লিসিট র্যাপ + fail-closed |
| বিদ্যমান ডেটা ব্যাকফিল ত্রুটি | সম্পূর্ণ বিদ্যমান ডেটা | ইডেমপোটেন্ট স্ক্রিপ্ট + ব্যাকফিল যাচাই + ড্রাই-রান মোড |
| ইনডেক্স/পারফরম্যান্স প্রভাব | হাই-ফ্রিকোয়েন্সি টেবিল (fee_bill/room/owner) | (tenant_id, community_id) কম্পাউন্ড ইনডেক্স; স্লো কোয়েরি লগ পুনঃপরীক্ষা |
| ১৩৩ টেস্ট রিগ্রেশন | সম্পূর্ণ | scope ইনজেকশনের পর প্রথমে সম্পূর্ণ রিগ্রেশন চালান, তারপর পাইলট চালু |
| নাম বিভ্রান্তি (management_tenant ভাড়াটে vs SaaS টেন্যান্ট) | ডেভেলপমেন্ট কগনিশন | নতুন টেবিলের নাম platform_tenant, ডকুমেন্টে এক্সপ্লিসিট ঘোষণা |
| **রোলব্যাক সমাধান** | — | গ্লোবাল স্কোপ কনফিগ সুইচ দিয়ে এক-ক্লিকে বন্ধ করা যায় (সিঙ্গেল-টেন্যান্ট সেমান্টিক পুনরুদ্ধার), ডেটা কলাম রাখা হয় মুছে না, কোনো ডেস্ট্রাকটিভ পরিবর্তন নেই |

## 6. পর্যালোচনা উপসংহার

**এখনই করার পরামর্শ**:
- শেয়ার্ড ডেটাবেস + tenant_id সারি আইসোলেশন (সমাধান A), নতুন `management_platform_tenant` টেবিল, community/admin_user-এ কলাম যোগ
- TenantContext মিডলওয়্যার + TenantScope গ্লোবাল স্কোপ + Tenant::for() টুল
- পাইলট ক্রম: গ্রুপ → কমিউনিটি → মালিক → ফি
- পূর্বশর্ত: সম্পন্ন হয়েছে — মাল্টি-টেন্যান্ট টেবিল/কলাম/ব্যাকফিল docs/install.sql-এ ইনলাইন করা হয়েছে (2026-08-16 একত্রিত, সিঙ্গেল ডেটাবেস তৈরির এন্ট্রি)

**পরে করার পরামর্শ**:
- আলাদা ডেটাবেস আইসোলেশন (B): শুধু সিঙ্গেল টেন্যান্ট >৫০ লাখ সারি বা কমপ্লায়েন্স প্রয়োজন হলে শুরু, ডেটা মডেল রিজার্ভ করা আছে
- হাইব্রিড সমাধান (C): পেমেন্ট/ফেসিয়াল ইত্যাদি শক্তিশালী আইসোলেশন দৃশ্যে ক্লায়েন্ট স্পষ্টভাবে চাইলে মূল্যায়ন

**করা উচিত নয়**:
- Schema-স্তরের আইসোলেশন (MySQL-এ আলাদা schema সেমান্টিক নেই, খরচ আলাদা ডেটাবেসের সমান)
- ডায়নামিক মাল্টি-ডেটাবেস রাউটিং (সিঙ্গেল মেশিন ডিপ্লয়মেন্টে কোনো লাভ নেই)
- টেন্যান্ট-স্তরের ব্যক্তিগতকৃত schema/ফিল্ড (YAGNI)
- management_tenant ভাড়াটে টেবিল পুনঃব্যবহার/রিফ্যাক্টর করে SaaS টেন্যান্ট বানানো (সেমান্টিক দ্বন্দ্ব, ভাড়াটে ব্যবসা নষ্ট)
