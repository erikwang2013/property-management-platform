## 2. বর্তমান প্রশমন (ইতিমধ্যে বাস্তবায়িত)

- **ব্যাকআপ**: সিঙ্গেল এন্ট্রি ব্যাকআপ স্ক্রিপ্ট `scripts/backup.sh` (`admin/.env` থেকে কানেকশন পড়ে, ডিফল্ট কন্টেইনারে mysqldump), প্রতিদিন crontab ফুল ব্যাকআপ, ডিফল্ট ৭ দিন সংরক্ষণ (`--keep-days=30` কনফিগারযোগ্য); রিকভারি ড্রিল প্রক্রিয়া ও RPO/RTO ব্যাখ্যা দেখুন OPS_RUNBOOK §1 ও RECOVERY_RUNBOOK।
- **মনিটরিং অ্যালার্ট**: Prometheus + Grafana + `deploy/monitoring/alerts.yml`, AppDown / MysqlDown / RedisDown / ElasticsearchDown / QueueBacklog কভার করে, দেখুন OPS_RUNBOOK §3।
- **লগ রোটেশন**: কন্টেইনার লগ `max-size 10m`, হোস্ট মেশিন লগ logrotate প্রতিদিন রোটেশন ৩০ দিন সংরক্ষণ, দেখুন OPS_RUNBOOK §4।
- **অ্যাপ্লিকেশন স্তর**: webman মাল্টি-প্রসেস স্থায়ী, কিউ টাস্ক দিয়ে ধীর অপারেশন ডিকাপল, `/health` হেলথ চেক।

উপসংহার: উপরের প্রশমন "ফেইলিওর থেকে রিকভারি" কভার করে, **"ফেইলিওরে পরিষেবা বিঘ্ন না হওয়া" কভার করে না**। ব্যবসা বিঘ্ন অগ্রহণযোগ্য হলে §3-এর অনুভূমিক সম্প্রসারণে যেতে হবে।

## 3. অনুভূমিক সম্প্রসারণের পথ (অগ্রাধিকার অনুযায়ী)

সম্প্রসারণের মূল নীতি: প্রথমে উল্লম্ব (CPU/মেমরি/ডিস্ক বাড়ানো) পরে অনুভূমিক (কম্পোনেন্ট আলাদা করা), প্রথমে মিডলওয়্যার পরে অ্যাপ্লিকেশন, প্রতিটি ধাপ আলাদাভাবে রোলব্যাকযোগ্য।

### 3.1 MySQL মাস্টার-স্লেভ + সেমি-সিঙ্ক (প্রথম অগ্রাধিকার)

- আর্কিটেকচার: মাস্টার (বর্তমান ইনস্ট্যান্স) → স্লেভ (নতুন মেশিন), সেমি-সিঙ্ক রেপ্লিকেশন চালু (`rpl_semi_sync_master_enabled=1`)।
- রিড সম্প্রসারণ: অ্যাপ্লিকেশনে মাস্টার-স্লেভ সেপারেশন কনফিগার (`config/database.php` রিড-রাইট সেপারেশন সমর্থন করলে চালু করুন; না হলে আগে শুধু মাস্টার-স্লেভ হাই অ্যাভেইলেবিলিটি)।
- ব্যাকআপ মাইগ্রেশন: ব্যাকআপ স্ক্রিপ্ট স্লেভের দিকে করুন, যাতে ব্যাকআপ মাস্টারকে চাপ না দেয়।
- ভার্সন: স্লেভকে মাস্টারের মেজর ভার্সনের সাথে মিলতে হবে (বর্তমান 8.0.36)।
- আপগ্রেড শর্ত: মাস্টার CPU ক্রমাগত >70%, কানেকশন সংখ্যা max_connections-এর কাছাকাছি, স্লো কোয়েরি লগে স্ক্যান করা সারি সংখ্যা হঠাৎ বাড়া।

### 3.2 Redis সেন্টিনেল বা ক্লাস্টার (দ্বিতীয় অগ্রাধিকার)

- সেন্টিনেল (৩ নোড): ক্যাপাসিটি চাহিদা কম হলে সেন্টিনেল বেছে নিন, সুইচ সেকেন্ড-স্তরের, ক্লায়েন্টকে `sentinel` মোড সমর্থন করতে হবে।
- Cluster (≥৩ মাস্টার ৩ স্লেভ): ক্যাশে ভলিউম > সিঙ্গেল মেশিন মেমরি, বা লেখার কনকারেন্সি বাড়লে Cluster বেছে নিন।
- লক্ষ্য করুন: কিউ ও ডিস্ট্রিবিউটেড লক Redis-এর উপর নির্ভর করে, টপোলজি বদলালে `config/redis.php`-ও সিঙ্ক করতে হবে এবং ফল্ট ট্রান্সফারের অধীনে লক/কিউর আচরণ যাচাই করতে হবে।

### 3.3 Elasticsearch আলাদা নোড

- সিঙ্গেল নোড ES-এ রেপ্লিকা নেই, ইনডেক্স নষ্ট হলে সার্চই অপ্রাপ্য। অন্তত আলাদা মেশিনে মাইগ্রেট + ১ রেপ্লিকা।
- ডেটা ভলিউম বাড়লে ইনডেক্স বিভক্ত করুন (বিজনেস ডোমেইন অনুযায়ী), অপ্রয়োজনীয় ইনডেক্স রেপ্লিকা বন্ধ করে রিসোর্স নিয়ন্ত্রণ করুন।
- আপগ্রেড শর্ত: হিপ মেমরি ব্যবহার >70% স্থায়ী, রাইট রিজেক্ট (`es_rejected_executions` বাড়া), কোয়েরি P95 ১ সেকেন্ডের বেশি।

### 3.4 অ্যাপ্লিকেশন মাল্টি-রেপ্লিকা + লোড ব্যালান্সার (সবশেষ)

- admin/service প্রতিটিতে ২+ রেপ্লিকা, সামনে nginx লোড ব্যালান্সিং (রাউন্ড-রবিন বা least_conn)।
- পূর্বশর্ত: স্টেটলেস (session Redis-এ, লোকাল ফাইল রাইট নির্ভরতা নেই; এই সিস্টেম JWT + Redis session, মোটামুটি পূরণ হয়)।
- পরে রেপ্লিকা সংখ্যা অনুযায়ী প্রসেসিং ক্ষমতা দ্বিগুণ, তারপর §3.1-3.3-এর মিডলওয়্যার বাধায় ফিরুন।

## 4. ডেটা ভলিউম বৃদ্ধির ট্রিগার পয়েন্ট ও পরামর্শ

| ট্রিগার পয়েন্ট | থ্রেশহোল্ড পরামর্শ | অবশ্যই করতে হবে |
|--------|----------|----------|
| ডেটাবেস মোট | > 50GB বা একক টেবিল > ৫ কোটি সারি | মাস্টার-স্লেভ বিভাজন + পুরনো বিল/লগ টেবিল আর্কাইভ |
| স্লো কোয়েরি | দৈনিক স্লো কোয়েরি > ১০টি বা একক > 2s | ইনডেক্স যোগ, টেবিল ভাগ, N+1 পরীক্ষা |
| MySQL কানেকশন | স্থায়ী > 80% max_connections | কানেকশন পুল + মাস্টার-স্লেভ |
| Redis মেমরি | > 70% এবং ক্রমাগত বাড়ছে | মেয়াদোত্তীর্ণ কী পরিষ্কার → সেন্টিনেল → Cluster |
| ES হিপ মেমরি | > 70% বা রাইট রিজেক্ট | আলাদা নোড + রেপ্লিকা + ইনডেক্স বিভাজন |
| CPU | সিঙ্গেল কোর স্থায়ী > 80% এবং কিউ জমা | অ্যাপ্লিকেশন মাল্টি-রেপ্লিকা → মিডলওয়্যার বিভাজন |
| ডিস্ক | > 80% | ব্যাকআপ/লগ পরিষ্কার, কোল্ড ডেটা আর্কাইভ |

পরামর্শ: প্রতি মাসে উপরের টেবিল একবার মিলিয়ে দেখুন (ডেটা Grafana প্যানেল থেকে নেওয়া যায়), যেকোনো একটি আইটেম টানা দুই সপ্তাহ থ্রেশহোল্ড ছাড়ালে সংশ্লিষ্ট সম্প্রসারণ শুরু করুন।

## 5. সম্প্রসারণ ড্রিল পরামর্শ

- **প্রতি ত্রৈমাসিকে একবার**: রিকভারি ড্রিল (দেখুন OPS_RUNBOOK §1.3), RPO/RTO অর্জন যাচাই।
- **প্রতি বছর একবার**: মাস্টার-স্লেভ সুইচ ড্রিল (নতুন মেশিনে ড্রিল করুন, প্রোডাকশন মাস্টার স্পর্শ করবেন না): স্লেভ তৈরি → ক্যাচ-আপ → সুইচ → দুই পাশের রিড-রাইট যাচাই → ফিরে সুইচ।
- **প্রথম সম্প্রসারণের পরে**: `scripts/loadtest` দিয়ে তিনটি পথ (লগইন/লিস্ট/সার্চ) লোড টেস্ট করে P95 অর্জন নিশ্চিত করুন (রেফারেন্স `docs/PERFORMANCE_REPORT_2026-08-16.md`)।
- **ড্রিল রেকর্ড**: প্রতিটি ড্রিল CHANGELOG.md-এ লিখুন, সহ: সময়, ড্রিল আইটেম, ফলাফল, অবশিষ্ট সমস্যা।

## 6. আপগ্রেড পাথ কুইক রেফারেন্স

```
সিঙ্গেল মেশিন (বর্তমান)
  ├─ MySQL মাস্টার-স্লেভ সেমি-সিঙ্ক      ← প্রথম অগ্রাধিকার
  ├─ Redis সেন্টিনেল/Cluster              ← দ্বিতীয় অগ্রাধিকার
  ├─ ES আলাদা নোড+রেপ্লিকা                ← তৃতীয় অগ্রাধিকার
  └─ অ্যাপ্লিকেশন মাল্টি-রেপ্লিকা+LB       ← সবশেষ
        ↓
মাল্টি-মেশিন ডিপ্লয়মেন্ট (কোনো সিঙ্গেল পয়েন্ট নেই, ফল্ট বিঘ্ন গ্রহণযোগ্য → মিনিট-স্তরের বিঘ্ন গ্রহণযোগ্য → সেকেন্ড-স্তরের সুইচ)
```

> বর্তমান ব্যবসার ভলিউমে সম্প্রসারণের প্রয়োজন নেই, এই ডকুমেন্ট "ডেটা ভলিউম/ফল্ট প্রয়োজন পরিবর্তন হলে" সরাসরি অনুসরণ করার জন্য, ঘটনাস্থলে সিদ্ধান্ত নেওয়া এড়াতে।
