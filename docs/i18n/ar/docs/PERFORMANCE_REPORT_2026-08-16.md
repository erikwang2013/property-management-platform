## 1. بيئة الاختبار والمنهجية

| البند | القيمة |
|---|---|
| التطبيق | webman v2 (PHP 8.3، 32 workers)، تطبيقا admin + service |
| المثيل المُختبر | admin منفذ مستقل 8790 (`SERVER_LISTEN=http://0.0.0.0:8790`) |
| الأداة | k6 v0.51.0 (لا يوجد wrk/ab/hey محليًا)، السكربتات في `scripts/loadtest/` |
| أهداف الاختبار | تسجيل الدخول (/api/auth/login)، لوحة القيادة (/admin/dashboard)، قائمة دفع الرسوم (/admin/fee-payment) |
| المصادقة | dashboard/fee تستخدم `scripts/loadtest/mint-token.php` لإصدار JWT (تجاوز رمز التحقق، `sub=21000000000000100`)؛ سكربت الدخول يستخدم رمز تحقق غير صالح لاستكشاف السلسلة |
| البيانات | اتصال مباشر أحادي 127.0.0.1 بدون بوابة/CDN؛ MySQL/Redis والتطبيق على نفس الجهاز |

مدخل السكربت: `bash scripts/loadtest/run.sh [BASE_URL] [VUS] [DURATION]` (يتطلب k6 في PATH).
ملاحظة سكربت الدخول: الدخول محمي مزدوجًا برمز التحقق + تحديد المعدل (10 مرات/دقيقة/IP)، وهو تصميم أمني ولا يمكن ولا ينبغي اختباره بضغط عالٍ؛ login.js يختبر تأخير السلسلة بمعدل منخفض 1 VU / 8 طلبات، والمتوقع إرجاع 422 (رمز تحقق خاطئ) أو 429 (تحديد معدل)، وكلاهما دليل أن الدفاع يعمل بشكل طبيعي.

### الخلاصة

- جميع الواجهات تحت 20 VU: 0 فشل، p95 < 220ms، سليمة.
- **عنق الإنتاجية نحو 230–250 rps**: من 20 VU إلى 50 VU الإنتاجية لا ترتفع بل تستوي (dashboard 227.9 ← 226.9، fee 197 ← 247)، بينما يتضاعف تأخير p95 (~190ms ← ~540ms). مع 32 worker على جهاز واحد كل worker نحو 7–8 rps، وهي خاصية حد النواة الواحدة لسلسلة PHP الكاملة (شاملة استعلامات MySQL وذهاب وإياب ذاكرة Redis)، وليست نفاد اتصالات (لا طلبات فاشلة).
- الاقتراح: هذا الحجم أحادي كافٍ بالفعل (نحو 20 مليون طلب/يوم)؛ إذا أردت إنتاجية أعلى، فضّل إضافة مثيلات أفقية، ثم فحص SQL ومدى إصابة الذاكرة لكل واجهة (انظر أدناه).

## 3. مراجعة الاستعلامات البطيئة

- فهارس جداول الرسوم `management_fee_bill` / `management_fee_payment` مكتملة (paid_at، bill_id، owner_id، payment_number وغيرها)، والاستعلامات الأساسية كلها لها فهارس قابلة للاستخدام.
- نقطة مكتشفة: بحث قائمة الرسوم بفهرس مسبق `payment_number like %kw%` (حرف بدل في البداية)، لا يمكنه استخدام الفهرس، ومع كبر حجم البيانات يتدهور الشرط إلى فحص جدول كامل. بحث إدارة منخفض التردد، لا يُعالج حاليًا؛ بعد نمو البيانات يمكن التحويل إلى فهرس مقلوب أو فهرس بادئة.
- **MySQL slow_query_log في OFF**: يُقترح تشغيله وضبط `long_query_time=1`، لمراقبة الاستعلامات البطيئة الفعلية باستمرار (بدل الاستدلال من الاختبار). التنفيذ في الإنتاج:
  ```sql
  SET GLOBAL slow_query_log = ON;
  SET GLOBAL long_query_time = 1;
  ```
- تجميع لوحة القيادة: كل إعادة بناء للذاكرة تنفذ نحو 8 تجميعات COUNT + إحصاءات تجميع 30 يومًا، وإعادة البناء الواحدة تكلفة ثوانٍ، تمتصها ذاكرة Redis 5 دقائق (انظر أدناه)، وليست مسارًا حارًا.

## 4. مراجعة ذاكرة Redis

- ذاكرة لوحة القيادة `dashboard:data`: `setex 300`، عند الإصابة ~10ms، عند عدم الإصابة إعادة بناء بالثواني. **المشكلة: لا يوجد أي منطق إبطال عند عمليات الكتابة**، بعد تغيير البيانات تظل قديمة حتى 5 دقائق. يُقترح حذف المفتاح في واجهات كتابة الرسوم/العقارات (سطر واحد `del dashboard:data`).
- **لا حماية من اختراق الذاكرة**: لحظة انتهاء المفتاح تعيد 32 worker البناء معًا (تنفيذ مكرر لاستعلامات التجميع الثمانية). بعد كبر حجم البيانات يُقترح إضافة استبعاد متبادل بسيط (مثل قفل `set nx ex` + فحص مزدوج).
- ذاكرة الصلاحيات `perm:{adminId}` 60s، السلوك طبيعي.
- بند تحقق متبقٍ: لم يُلاحظ مفتاح `dashboard:data` أبدًا في Redis المحلي (لا في أي db)، لكن استجابة الواجهة طبيعية وتأخير الإصابة أقل بوضوح. أثناء الاختبار حدثت 403 عشوائية «لا إذن للوصول» (ظهرت مرتين ثم استقرت 200). يُشتبه في وجود مثيلات Redis متعددة/اختلاف إعداد متغيرات البيئة عن الإنتاج، يحتاج إعادة تحقق في البيئة الهدف، لا يؤثر على خلاصة الاختبار (0 فشل في الفترة المستقرة).
