# خطة التوسع (Scaling Plan)

> Copyright (c) 2026 erik <erik@erik.xyz> — https://erik.xyz

النشر الحالي docker-compose أحادي الجهاز (MySQL/Redis/Elasticsearch والتطبيق على نفس الجهاز، انظر `admin/docker-compose.yml`)، بلا HA. توضح هذه الوثيقة المخاطر والتخفيفات الحالية، وتعطي مسار التوسع الأفقي ونقاط تشغيل نمو البيانات واقتراحات التمرين. خط الأساس التشغيلي (النسخ الاحتياطي/الاستعادة، مراقبة الإنذار، تدوير السجلات) في [OPS_RUNBOOK.md](OPS_RUNBOOK.md).

### 1.2 قائمة المخاطر

| الخطر | الأثر | الاحتمال | العواقب |
|------|------|------|------|

| النسخ الاحتياطي/الاستعادة بلا تمرين | استعادة متأخرة أو فاشلة | متوسط | عالٍ |

## 2. التخفيفات الحالية (منفذة)

- **النسخ الاحتياطي**: سكربت نسخ احتياطي بمدخل واحد `scripts/backup.sh` (يقرأ الاتصال من `admin/.env`، افتراضيًا mysqldump داخل الحاوية)، نسخ احتياطي كامل يومي عبر crontab، الاحتفاظ الافتراضي 7 أيام (`--keep-days=30` قابل للتكوين)؛ سير تمرين الاستعادة وشرح RPO/RTO في OPS_RUNBOOK §1 و RECOVERY_RUNBOOK.
- **مراقبة الإنذار**: Prometheus + Grafana + `deploy/monitoring/alerts.yml`، تغطي AppDown / MysqlDown / RedisDown / ElasticsearchDown / QueueBacklog، انظر OPS_RUNBOOK §3.
- **تدوير السجلات**: سجلات الحاويات `max-size 10m`، سجلات المضيف logrotate تدوير يومي مع الاحتفاظ 30 يومًا، انظر OPS_RUNBOOK §4.
- **طبقة التطبيق**: عمليات webman متعددة مقيمة، مهام قائمة الانتظار تفصل العمليات المكلفة، فحص صحة `/health`.

الخلاصة: التخفيفات المذكورة تغطي «استعادة بعد الفشل»، **ولا تغطي «عدم انقطاع عند الفشل»**. عندما يكون الانقطاع غير مقبول تجاريًا، يلزم الدخول في التوسع الأفقي §3.

## 3. مسار التوسع الأفقي (حسب الأولوية)

المبدأ العام للتوسع: عموديًا أولًا (إضافة CPU/ذاكرة/قرص) ثم أفقيًا (فصل المكونات)، الوسطيات أولًا ثم التطبيق، وكل خطوة قابلة للتراجع بشكل مستقل.

### 3.1 MySQL رئيسي-تابع + شبه متزامن (الأولوية الأولى)

- البنية: قاعدة رئيسية (المثيل الحالي) ← قاعدة تابعة (جهاز جديد)، تفعيل النسخ شبه المتزامن (`rpl_semi_sync_master_enabled=1`).
- توسعة القراءة: فصل القراءة/الكتابة في إعداد التطبيق (فعّل عند دعم `config/database.php` لفصل القراءة/الكتابة؛ وإلا ابدأ بتحقيق HA رئيسي-تابع فقط).
- ترحيل النسخ الاحتياطي: سكربت النسخ الاحتياطي يوجه إلى القاعدة التابعة، لتجنب ضغط القاعدة الرئيسية بالنسخ.
- الإصدار: يجب أن تتطابق القاعدة التابعة مع الرئيسية في الإصدار الرئيسي (الحالي 8.0.36).
- شروط الترقية: CPU القاعدة الرئيسية > 70% باستمرار، الاتصالات قريبة من max_connections، قفزة في عدد الصفوف المفحوصة في سجلات الاستعلامات البطيئة.

### 3.2 Redis Sentinel أو Cluster (الأولوية الثانية)

- Sentinel (3 عقد): اختر Sentinel عندما لا تكون متطلبات السعة عالية، التبديل بالثواني، العميل يجب أن يدعم وضع `sentinel`.
- Cluster (≥ 3 رئيسية و 3 تابعة): اختر Cluster عندما تتجاوز كمية الذاكرة ذاكرة جهاز واحد، أو يرتفع التزامن في الكتابة.
- ملاحظة: قائمة الانتظار والأقفال الموزعة تعتمدان على Redis، عند تغيير الطوبولوجيا يجب تعديل `config/redis.php` والتحقق من سلوك الأقفال/قائمة الانتظار تحت تجاوز الفشل.

### 3.3 عقدة Elasticsearch مستقلة

- ES أحادي العقدة بلا نسخ، تلف الفهرس يعني تعطل البحث. انقل على الأقل إلى جهاز مستقل + نسخة واحدة.
- بعد نمو البيانات قسّم الفهرس (حسب مجال الأعمال)، وأغلق النسخ غير الضرورية للفهارس للتحكم في الموارد.
- شروط الترقية: استخدام ذاكرة الكومة > 70% مستمر، رفض الكتابة (ارتفاع `es_rejected_executions`)، تجاوز p95 للاستعلام 1s.

### 3.4 نسخ تطبيق متعددة + موازنة تحميل (أخيرًا)

- admin/service كلٌّ بمثيلين+، أمامهما nginx موازنة تحميل (round-robin أو least_conn).
- الشروط المسبقة: عديم الحالة (الجلسات في Redis، لا اعتماد على كتابة ملفات محلية؛ النظام الحالي JWT + جلسات Redis، مُلبّاة أساسًا).
- بعدها تتضاعف قدرة المعالجة بعدد النسخ، ثم نعود إلى عنق الوسطيات في §3.1-3.3.

## 4. نقاط تشغيل نمو البيانات والاقتراحات

| نقطة التشغيل | عتبة الاقتراح | الإجراء الإلزامي |
|--------|----------|----------|
| إجمالي قاعدة البيانات | > 50GB أو جدول واحد > 50 مليون صف | فصل رئيسي-تابع + أرشفة جداول الفواتير/السجلات التاريخية |
| الاستعلامات البطيئة | أكثر من 10 يوميًا أو واحدة > 2s | إضافة فهارس، تقسيم الجداول، فحص N+1 |
| اتصالات MySQL | باستمرار > 80% من max_connections | تجميع الاتصالات + رئيسي-تابع |
| ذاكرة Redis | > 70% وتنمو باستمرار | تنظيف المفاتيح المنتهية ← Sentinel ← Cluster |
| ذاكرة كومة ES | > 70% أو رفض كتابة | عقدة مستقلة + نسخ + تقسيم فهرس |
| CPU | نواة واحدة > 80% باستمرار مع تراكم قائمة انتظار | نسخ تطبيق متعددة ← فصل الوسطيات |
| القرص | > 80% | تنظيف النسخ الاحتياطي/السجلات، أرشفة البيانات الباردة |

اقتراح: راجع الجدول أعلاه شهريًا (يمكن أخذ البيانات من لوحات Grafana)، وأي بند يتجاوز العتبة لأسبوعين متتاليين ابدأ التوسع المقابل.

## 5. اقتراحات تمرين التوسع

- **ربع سنوي**: تمرين الاستعادة (انظر OPS_RUNBOOK §1.3)، تحقق من بلوغ RPO/RTO.
- **سنوي**: تمرين تبديل رئيسي-تابع (تمرّن على جهاز جديد، لا تلمس القاعدة الرئيسية في الإنتاج): أنشئ التابعة ← اللحاق ← التبديل ← تحقق من قراءة/كتابة الطرفين ← الإعادة.
- **بعد أول توسع**: استخدم `scripts/loadtest` لاختبار المسارات الثلاثة (تسجيل الدخول/القائمة/البحث) للتأكد من بلوغ P95 (راجع `docs/PERFORMANCE_REPORT_2026-08-16.md`).
- **سجل التمارين**: كل تمرين يُسجل في سجل التغييرات (CHANGELOG.md)، شاملاً: الوقت، بند التمرين، النتيجة، المشكلات المتبقية.

## 6. مرجع سريع لمسار الترقية

```
أحادي الجهاز (الوضع الحالي)
  ├─ MySQL رئيسي-تابع شبه متزامن    ← الأولوية الأولى
  ├─ Redis Sentinel/Cluster          ← الأولوية الثانية
  ├─ ES عقدة مستقلة + نسخ             ← الأولوية الثالثة
  └─ نسخ تطبيق متعددة + LB            ← أخيرًا
        ↓
نشر متعدد الأجهزة (بلا نقطة فشل واحدة، يمكن قبول انقطاع الفشل ← يمكن قبول انقطاع بالدقائق ← تبديل بالثواني)
```

> مع حجم الأعمال الحالي لا حاجة للتوسع، هذه الوثيقة لـ«عند تغير متطلبات البيانات/الفشل» تُطبق مباشرة، تفاديًا للقرارات اللحظية.
