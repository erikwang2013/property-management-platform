## 1. جرد الوضع الحالي

### 1.1 تصنيف بنية الجداول (65 جدولًا، تحقق docs/install.sql)

| الفئة | الجداول | الوصف |
|------|-----|------|
| جداول عامة/منصة | erik_admin_user / admin_role / admin_permission / admin_user_role / admin_role_permission، erik_system_config، erik_operation_log | مصادقة، إعدادات، تدقيق، طبيعتها منصة، لا تُربط بمستأجر |
| جداول بعد المجتمع | erik_community و40+ جدول أعمال تتبع community_id (building/unit/room/owner/fee_*/repair_order/parking_*/announcement وغيرها) | تتبع المستأجر بشكل غير مباشر عبر community_id |
| جداول ربط المجموعة | erik_group (مجموعة)، erik_group_community (مجموعة↔مجمع) | حاليًا **ربط اختياري**، بلا دلالة مستأجر، التجميع عبر المجمعات يتم بالـ join |
| جداول تمديد المنصة | erik_notification_template، erik_knowledge_base، erik_mall_*، erik_face_info وغيرها | بعضها مستوى منصة وبعضها مستوى مجتمع، يحتاج تأكيدًا لكل حالة |
| جداول سهلة الالتباس | **erik_tenant (جدول المستأجرين السكنيين)** | ⚠️ تعارض دلالي: هو «مستأجر عقاري» (ببعد room_id/owner_id)، **ليس** مستأجر SaaS |

### 1.2 سلسلة المصادقة (طرف admin، تحقق بالكود)

```
وسيطة عامة: Cors → SecurityFilter → RateLimit
وسيطة مجموعة المسارات: AdminAuth(JWT → $request->adminId) → AdminPermission(RBAC method.path) → OperationLog → Controller
```

- `AdminAuth` أسس نمط حقن الطلب (`$request->adminId`)، وسياق المستأجر يمكن نسخه بالكامل
- `AdminPermission` RBAC على مستوى المنصة، **متعامد** مع عزل المستأجر، ويمكن تراكبهما
- طرف service للبوابة: JWT يحمل owner_id، والبيانات مقيدة طبيعيًا عبر room_owner → room.community_id، خطر العبور بين المستأجرين منخفض

### 1.3 الخلاصات الرئيسية

- لا يوجد أي نموذج SaaS مستأجر جاهز؛ اسم `erik_tenant` مشغول بالمستأجر السكني، والمفهوم الجديد يجب أن يتجنب الاسم
- كل المتحكمات تستعلم Eloquent مباشرة، بلا طبقة repository وبلا نطاق عام — إصلاح العزل يجب أن يتم في طبقة النماذج
- config/database.php اتصال واحد، لكن illuminate/database يدعم اتصالات متعددة أصليًا (محجوز لتطور القاعدة المستقلة)

## 2. مقارنة الحلول والتوصية

| الحل | الآلية | حجم التعديل | تكلفة التشغيل | الأنسب لـ |
|------|------|--------|----------|------|
| **أ. قاعدة مشتركة + عزل صفوف tenant_id (موصى به)** | جدول مستأجرين + عمود tenant_id في جداول الأعمال + نطاق Eloquent عام للتصفية | متوسط (إضافة أعمدة لجدولين + وسيطة + نطاق عام + إعادة تعبئة المخزون) | منخفض (النسخ الاحتياطي/الترحيل لقاعدة واحدة دون تغيير) | عقارات صغيرة/متوسطة، مستأجر واحد < 5 ملايين صف |
| ب. قاعدة مستقلة (قاعدة لكل مستأجر) | توجيه الاتصال + تجميع عبر القواعد | عالٍ (إدارة الاتصالات/تقارير عبر القواعد/ترحيل×N/نسخ احتياطي×N) | عالٍ | مجموعات كبيرة، متطلبات عزل امتثالي |
| ج. هجين (قواعد حساسة مستقلة + مشتركة) | تركيبة أ+ب | عالٍ | عالٍ | سيناريوهات عزل قوي كالدفع/الوجوه |

**التوصية أ، ب اتجاه تطور.** الأسباب:

1. الجداول الـ65 الحالية موحدة في قاعدة واحدة، نموذج بيانات tenant_id في أ لا يعيق تقسيم القاعدة مستقبلًا (تتغير دقة التصفية من صف إلى قاعدة، في أ يكون معرف المستأجر نموذجًا عامًا بالفعل)
2. بيانات الأعمال كلها تتبع community_id، tenant_id يحتاج فقط إلى **أعلى الجداول**، والجداول الـ40 الوسيطة مضمونة بمسار الوصول، تفاديًا لإضافة عمود لكل جدول
3. الطرفان (admin/service) يتشاركان نموذج البيانات نفسه، تعديل أ يتركز في طبقة تشغيل admin
4. تحت النشر الأحادي الحالي تعقيد النسخ الاحتياطي/الترحيل في ب غير محتمل

## 3. تصميم نقاط العزل

### 3.1 نموذج البيانات (الحد الأدنى)

- جدول جديد `erik_platform_tenant` (تجنبًا للتعارض مع جدول المستأجرين erik_tenant): id/name/status/created_at وغيرها
- `erik_community` يضاف `tenant_id BIGINT NOT NULL DEFAULT 0`، فهرس `(tenant_id, community_id)`
- `erik_admin_user` يضاف `tenant_id BIGINT NOT NULL DEFAULT 0` (0 = مدير المنصة الأعلى)
- جداول الأعمال الوسيطة (building/room/fee_bill وغيرها الـ40) **لا يضاف لها عمود**، تتبع عبر community_id

### 3.2 ثلاثية طبقة التشغيل

1. **وسيطة TenantContext**: حمولة JWT تزداد بمطالبة `tenant_id` → `$request->tenantId` (نسخ نمط حقن AdminAuth)؛ قائمة إعفاء لتسجيل الدخول/التثبيت/مسارات مستوى المنصة (user/role/permission/config)
2. **النطاق العام TenantScope**: للنماذج على مستوى المنصة وأعمال المجتمع، نطاق Eloquent عام يصفّي تلقائيًا حسب `$request->tenantId`؛ `find()` مقيد بالنطاق أيضًا، فيمنع طبيعيًا الاستعلام الفردي المباشر العابر للمستأجر
3. **سياق صريح Tenant::for()**: المهام المجدولة/قائمة الانتظار/الاستيراد بلا طلب HTTP، يُحدد المستأجر صراحةً بغلاف إغلاق؛ عند غياب السياق **fail-closed** (رفض الاستعلام)، لا يُسمح بالمرور الصامت بلا تصفية

### 3.3 نقاط اختبار حماية تجاوز الصلاحيات (مصفوفة القبول)

| الحالة | المتوقع |
|------|------|
| مدير مستأجر أ يعرض قائمة community/building/fee_bill لمستأجر ب | إرجاع فارغ أو بيانات أ فقط |
| مدير مستأجر أ يعمل find/update/delete على سجل مفرد لمستأجر ب (استعلام مباشر بالمعرف) | 403 / بيانات فارغة / رفض |
| مدير المنصة (tenant_id=0) عمليات عبر المستأجرين | إعفاء (قدرة مستوى المنصة) |
| عمليات بوابة الملاك عبر المجمعات (دفع/إصلاح) | رفض (تحقق انتماء community) |
| المهام المجدولة/قائمة الانتظار بلا سياق مستأجر | خطأ fail-closed لا مرور بلا تصفية |

## 4. مسار التطور (ترحيل مرحلي)

| الخطوة | المحتوى | القبول |
|------|------|------|
| 1. طبقة البيانات | إنشاء جدول platform_tenant + إضافة أعمدة community/admin_user + ترحيل idempotent + تهيئة المستأجر الافتراضي وإعادة تعبئة المخزون | كل community يجب أن يتبع مستأجرًا، تقرير البيانات اليتيمة صفر |
| 2. طبقة التشغيل | وسيطة TenantContext + TenantScope + أداة Tenant::for() + قائمة إعفاء المسارات | تراجع مستأجر واحد: اختبارات الـ133 كلها ناجحة |
| 3. وحدات تجريبية | إدارة المجموعة ← المجمع ← الملاك ← الرسوم (الفواتير) أربع وحدات تفعّل العزل أولًا | مصفوفة اختبار التجاوز ناجحة |
| 4. الانتشار الكامل | بالدفعات (الدفعة الأولى الأساسية ← الثانية المساعدة ← وحدات التمديد) تفعيل وحدة بوحدة | مصفوفة التجاوز لجميع الوحدات ناجحة |
| 5. التطور | بيانات مستأجر واحد > 5 ملايين صف أو متطلبات امتثال عندها تُقيّم تقسيم القاعدة (حل ب)، نموذج بيانات أ لا يعيق | مراجعة حل تقسيم القاعدة |

استراتيجية ترحيل البيانات: كل بيانات المخزون تُنقل إلى «المستأجر الافتراضي» (يُنشئه سكربت الترحيل)، دون حذف أو تعديل بيانات الأعمال؛ سكربت الترحيل idempotent، قابل للتنفيذ المتكرر.

## 5. قائمة المخاطر

| الخطر | نطاق الأثر | التخفيف / التراجع |
|------|--------|-------------|
| حجم تعديل مسارات استعلام 58+17 متحكمًا كبيرًا | كل واجهات الأعمال | النطاق العام يغطي ~80% من القوائم/التفاصيل؛ raw query والاستيراد الجماعي عبر Tenant::for()؛ رمادي تدريجي بالدفعات |
| النطاق العام يصيب استعلامات مستوى المنصة (تجميع لوحة القيادة عبر المجمعات) | لوحة القيادة/التقارير | واجهات مستوى المنصة تستخدم Tenant::without() صراحةً أو مسار جانبي tenant_id=0 |
| المهام المجدولة/قائمة الانتظار بلا سياق طلب | المهام الخلفية للتحصيل/SLA/الإشعارات وغيرها | غلاف صريح Tenant::for() + fail-closed |
| خطأ إعادة تعبئة المخزون | كل بيانات المخزون | سكربت idempotent + تحقق التعبئة + وضع تشغيل جاف |

| تراجع اختبارات الـ133 | الكل | بعد حقن النطاق شغّل التراجع الكامل أولًا ثم ابدأ التجريب |
| التباس التسمية (erik_tenant مستأجر سكني مقابل مستأجر SaaS) | وعي التطوير | تسمية الجدول الجديد platform_tenant، توثيق صريح |
| **خطة التراجع** | — | النطاق العام يمكن إيقافه بمفتاح إعداد بخطوة واحدة (استعادة دلالة المستأجر الواحد)، أعمدة البيانات تُبقي ولا تُحذف، بلا تغيير مدمر |

## 6. خلاصة المراجعة

**يُوصى بتنفيذه فورًا**:
- قاعدة مشتركة + عزل صفوف tenant_id (حل أ)، جدول جديد `erik_platform_tenant`، إضافة أعمدة community/admin_user
- وسيطة TenantContext + نطاق عام TenantScope + أداة Tenant::for()
- ترتيب التجربة: مجموعة ← مجمع ← ملاك ← رسوم
- الاعتماد المسبق: اكتمل — جداول/أعمدة/تعبئة متعدد المستأجرين مدمجة في docs/install.sql (دُمجت 2026-08-16، مدخل إنشاء قاعدة واحد)

**يُوصى بتأجيله**:
- عزل قاعدة مستقلة (ب): فقط عند مستأجر واحد > 5 ملايين صف أو متطلبات امتثال، نموذج البيانات محجوز مسبقًا
- الحل الهجين (ج): سيناريوهات العزل القوي كالدفع/الوجوه تُقيّم إذا طلبها العميل صراحةً

**لا يُوصى به**:
- عزل على مستوى Schema (MySQL بلا دلالة schema مستقلة، تكلفتها كالقاعدة المستقلة)
- توجيه ديناميكي متعدد القواعد (بلا فائدة تحت النشر الأحادي)
- schema/حقول مخصصة لكل مستأجر (YAGNI)
- إعادة استخدام/تعديل جدول المستأجرين erik_tenant ليكون مستأجر SaaS (تعارض دلالي، يكسر أعمال المستأجرين)
