> Copyright (c) 2026 erik <erik@erik.xyz> — https://erik.xyz
> Применимо: property-management-platform (админ-панель + портал жильцов, MySQL 8.0)
> Читать совместно с разделом 1 [OPS_RUNBOOK.md](OPS_RUNBOOK.md): создание резервных копий, crontab, RPO/RTO — в OPS_RUNBOOK, здесь только «как восстановить, как проверить».

## 0. Цель

- **Цель тренировки: полная тренировка восстановления за 30 минут** (восстановление + проверка), не реже одного раза в квартал.
- Имея в любой момент последнюю резервную копию, по этому документу можно восстановиться в пустую БД или на указанный момент времени.

Предварительные условия:

- Файл резервной копии доступен: `scripts/backup.sh` выполняется по cron (см. OPS_RUNBOOK 1.2).
- Среда восстановления (тренировочная или продовая машина) изоморфна проду: тот же docker-compose, та же версия MySQL 8.0.
- Перед восстановлением убедиться: `gzip -t <файл резервной копии>` проходит; свободное место на диске ≥ 2× объёма копии.

## 1. Сценарий A: восстановление в пустую БД (самый частый, сценарий тренировки по умолчанию)

Цель: импортировать копию в новую пустую БД и проверить доступность данных.

```bash
cd /path/to/property-management-platform

# 1) Выбрать последнюю резервную копию
ls -lt backups/backup_*.sql.gz | head

# 2) Проверка целостности (при неудаче — взять более раннюю копию)
gzip -t backups/backup_20260816_020000.sql.gz && echo OK

# 3) Убедиться, что целевой контейнер работает
docker compose -f admin/docker-compose.yml ps mysql

# 4) Создать пустую БД (в имени тренировочной БД суффикс _drill, чтобы не задеть прод-данные)
docker compose -f admin/docker-compose.yml exec -T \
  -e MYSQL_PWD=root mysql \
  sh -c 'mysql -uroot -e "CREATE DATABASE IF NOT EXISTS management_drill DEFAULT CHARACTER SET utf8mb4;"'

# 5) Импорт (-T отключает TTY, гарантирует неинтерактивность; фактически около 1-5 минут)
docker compose -f admin/docker-compose.yml exec -T \
  -e MYSQL_PWD=root mysql \
  sh -c 'mysql -uroot --default-character-set=utf8mb4 management_drill' \
  < backups/backup_20260816_020000.sql.gz
```

> Подсказка об учётных данных: `MYSQL_PWD` берётся из `DB_PASSWORD` в `admin/.env`; в проде запрещено оставлять пароль открытым в истории shell, рекомендуется `--env-file admin/.env` или внедрение переменных окружения. В этом руководстве примеры — согласованные значения тренировочной среды.

## 2. Сценарий B: восстановление на указанный момент времени (воспроизведение binlog)

Предпосылка: в MySQL 8 binlog включён по умолчанию (`log_bin=ON`), инкремент после момента резервной копии — в binlog. Потеря данных ≤ последняя копия + срок хранения binlog (по умолчанию `binlog_expire_logs_seconds=2592000`, 30 дней).

Идея: полное восстановление → найти начало binlog → воспроизвести `mysqlbinlog` до целевого момента.

```bash
# 1) Убедиться, что binlog включён, вывести файлы журналов
docker compose -f admin/docker-compose.yml exec -T \
  -e MYSQL_PWD=root mysql \
  sh -c 'mysql -uroot -e "SHOW VARIABLES LIKE \"log_bin\"; SHOW BINARY LOGS;"'

# 2) Полное восстановление (как сценарий A, шаги 4-5, в пустую БД)

# 3) Найти начало binlog для копии: позиция записана в файле копии (при --master-data=2).
#    У этого скрипта --master-data нет, начало = «момент начала резервирования», погрешность в пределах длительности копии.
#    Воспроизвести binlog до целевого момента (пример: до 2026-08-16 10:30:00)
docker compose -f admin/docker-compose.yml exec -T \
  -e MYSQL_PWD=root mysql \
  sh -c 'mysqlbinlog --stop-datetime="2026-08-16 10:30:00" /var/lib/mysql/binlog.000012 | mysql -uroot management_drill'
```

Ключевые моменты:

- Путь binlog в контейнере `/var/lib/mysql/binlog.0000NN`, сопоставляется по выводу `SHOW BINARY LOGS`.
- Воспроизводить только binlog «после момента начала копии»; сразу после воспроизведения проверить (см. раздел 3), убедиться, что `max(updated_at)` соответствует ожидаемому.
- Восстановление ошибочной операции с точностью до секунды: сначала найти операцию `mysqlbinlog /var/lib/mysql/binlog.0000NN | grep -n "ключевое слово ошибочной операции"`, затем выбрать `--stop-datetime` или `--stop-position`.

## 3. Проверка консистентности данных (обязательна после восстановления)

| Проверка | Команда | Критерий прохождения |
|---|---|---|
| Целостность файла копии | `gzip -t <копия>` | без ошибок |
| Число строк ключевых таблиц | `SELECT COUNT(*) FROM management_admin_user;` | совпадает с числом строк, записанным до копирования |
| Выборочная проверка бизнес-таблиц | `SELECT COUNT(*) FROM management_owner;`、`management_tenant`、`management_fee_bill`、`management_repair_order` | три и более таблиц в разумном порядке величины (не 0 и совпадают с состоянием до копирования) |
| Шифрованные поля расшифровываются | запросить запись с encryptable-полем (например, удостоверение/телефон в `management_owner`) | значение верное, в журнале приложения нет ошибок decrypt |
| Дымовая проверка бизнеса | вход и получение списка по 1 разу | 200 / нормальный ответ |

Пример скрипта выборочной проверки (тренировочная среда):

```bash
docker compose -f admin/docker-compose.yml exec -T -e MYSQL_PWD=root mysql \
  sh -c 'mysql -uroot management_drill -e "
    SELECT (SELECT COUNT(*) FROM management_admin_user) AS users,
           (SELECT COUNT(*) FROM management_owner) AS owners,
           (SELECT COUNT(*) FROM management_tenant) AS tenants,
           (SELECT COUNT(*) FROM management_fee_bill) AS fee_bills,
           (SELECT COUNT(*) FROM management_repair_order) AS repair_orders;"'
```

> Согласованность строк: до копирования записать базовую линию тем же SQL и сравнить после восстановления; при тренировке записать базовую линию в протокол тренировки.

## 4. Тайм-план 30-минутной тренировки

| Время | Действие | Ответственный |
|---|---|---|
| 0-5 мин | выбрать копию、`gzip -t`、создать пустую БД、записать базовые числа строк | эксплуатация |
| 5-15 мин | восстановление по сценарию A | эксплуатация |
| 15-25 мин | проверка консистентности по разделу 3 + дымовая проверка бизнеса | эксплуатация + бизнес |
| 25-30 мин | записать результат、удалить тренировочную БД (`DROP DATABASE management_drill`)、обновить фактический RTO в OPS_RUNBOOK 1.4 | эксплуатация |

## 5. Обработка сбоев

| Симптом | Обработка |
|---|---|
| `gzip -t` не прошёл | копия повреждена, взять более раннюю, принять больший RPO, проверить, что cron резервирования работает |
| Ошибка импорта (кодировка/права) | убедиться в согласованности `--default-character-set=utf8mb4` и кодировки пустой БД; убедиться, что у пользователя есть права на создание таблиц |
| Число строк не совпадает с базовой линией | немедленно остановить тренировку, проверить, не импортирована ли не та БД/не тот файл; в прод-сценарии — продолжить разбор и откатить приложение |
| После воспроизведения binlog данных всё ещё не хватает | проверить, что `--stop-datetime` не раньше момента начала копии; убедиться, что воспроизведение начато с первого binlog после копии |

## 6. Шаблон протокола тренировки

```text
Дата: 2026-08-16
Цель восстановления: пустая БД (сценарий A) / момент времени (сценарий B)
Файл копии: backups/backup_20260816_020000.sql.gz
Базовая линия строк: management_admin_user=1, management_owner=42, management_fee_bill=128
Время восстановления: XX мин    Время проверки: XX мин    Итого: XX мин (цель ≤ 30)
Результат: прошла / не прошла (с причиной и обработкой)
```
