## 1. Среда и методика тестирования

| Пункт | Значение |
|---|---|
| Приложение | webman v2 (PHP 8.3, 32 workers), два приложения admin + service |
| Тестируемый экземпляр | admin на отдельном порту 8790 (`SERVER_LISTEN=http://0.0.0.0:8790`) |
| Инструмент | k6 v0.51.0 (на машине нет wrk/ab/hey), скрипты в `scripts/loadtest/` |
| Цели нагрузки | вход (/api/auth/login), дашборд (/admin/dashboard), список оплат (/admin/fee-payment) |
| Аутентификация | для dashboard/fee JWT выписывается `scripts/loadtest/mint-token.php` (в обход кода подтверждения, `sub=21000000000000100`); скрипт входа проверяет цепочку невалидным кодом |
| Данные | прямое подключение к 127.0.0.1 на одной машине, без шлюза/CDN; MySQL/Redis на той же машине, что и приложение |

Точка входа скриптов: `bash scripts/loadtest/run.sh [BASE_URL] [VUS] [DURATION]` (требуется k6 в PATH).
Пояснение к скрипту входа: вход защищён двойной защитой — код подтверждения + ограничение частоты (10 раз/мин/IP), это проектная мера безопасности, высоконагруженное тестирование входа невозможно и не должно проводиться; login.js пробивает задержку цепочки на низкой скорости — 1 VU / 8 запросов, ожидается 422 (ошибка кода подтверждения) или 429 (ограничение частоты) — в обоих случаях защита сработала штатно.

## 2. Результаты нагрузочного тестирования

### 20 VU / 30s (базовая нагрузка)

| Интерфейс | Запросов | Пропускная способность | avg | p90 | p95 | max | Доля ошибок |
|---|---|---|---|---|---|---|---|
| login (1 VU × 8 запросов) | 8 | 14.4/s | 68.6ms | 154ms | 207.8ms | 261ms | 0% |
| dashboard | 6863 | 227.9/s | 86.0ms | 151ms | 189.5ms | 1.37s | 0% |
| fee-payment | 5944 | 197.2/s | 99.3ms | 178ms | 220.0ms | 704ms | 0% |

### 50 VU / 30s (повышенная нагрузка)

| Интерфейс | Запросов | Пропускная способность | avg | p95 | max | Доля ошибок |
|---|---|---|---|---|---|---|
| login (1 VU × 8 запросов) | 8 | 18.7/s | 52.1ms | 173ms | 243.8ms | 0% |
| dashboard | 6902 | 226.9/s | 212.7ms | 544.0ms | 1.99s | 0% |
| fee-payment | 7525 | 247.4/s | 195.7ms | 514.2ms | 2.0s | 0% |

(При 50 VU p95 превышает порог 500ms, k6 фиксирует превышение порога и завершает работу, но 0% ошибок запросов, 0 ответов, отличных от 200.)

### Выводы

- При 20 VU все интерфейсы без ошибок, p95 < 220ms — состояние здоровое.
- **Узкое место пропускной способности ~230–250 rps**: при переходе 20 VU → 50 VU пропускная способность не растёт, а выравнивается (dashboard 227.9 → 226.9, fee 197 → 247), при этом p95 удваивается (~190ms → ~540ms). При 32 workers на одной машине ~7–8 rps на worker — это характеристика предела одного ядра на полной цепочке PHP (запросы MySQL, обмен с кэшем Redis), а не исчерпание соединений (запросов с ошибками нет).
- Рекомендация: для одной машины этого масштаба достаточно (~20 млн запросов/день); для большей пропускной способности сначала добавлять горизонтальные инстансы, затем разбирать SQL и попадание в кэш каждого интерфейса (см. ниже).

## 3. Аудит медленных запросов

- Индексы таблиц платежей `management_fee_bill` / `management_fee_payment` в порядке (paid_at、bill_id、owner_id、payment_number и др.), для ключевых запросов индексы доступны.
- Найденный момент: нечёткий поиск списка платежей по `payment_number like %kw%` (ведущий подстановочный знак) не использует индекс, при больших объёмах данных условие выродится в полное сканирование таблицы. Это редкий поиск админ-панели, пока не обрабатывается; при росте данных можно перейти на инвертированный или префиксный индекс.
- **MySQL slow_query_log выключен (OFF)**: рекомендуется включить с `long_query_time=1` и непрерывно наблюдать реальные медленные SQL (а не судить по нагрузочному тесту). В проде выполнить:
  ```sql
  SET GLOBAL slow_query_log = ON;
  SET GLOBAL long_query_time = 1;
  ```
- Агрегация дашборда: при каждом перестроении кэша выполняется ~8 COUNT-агрегаций + группировка за 30 дней, одно перестроение стоит секунды, поглощается 5-минутным кэшем Redis (см. ниже), не горячий путь.

## 4. Повторная проверка кэша Redis

- Кэш дашборда `dashboard:data`: `setex 300`, при попадании ~10ms, при промахе перестроение за секунды. **Проблема: нет логики инвалидации при записи** — после изменения данных данные устаревают до 5 минут. Рекомендуется удалять этот ключ в интерфейсах записи платежей/объектов (одна строка `del dashboard:data`).
- **Нет защиты от пробоя кэша**: в момент истечения ключа 32 worker перестраивают одновременно (повторное выполнение 8 агрегационных запросов). При росте данных рекомендуется простая взаимоисключающая блокировка (например, `set nx ex` + двойная проверка).
- Кэш прав `perm:{adminId}` 60s — поведение нормальное.
- Остаточный пункт расследования: на локальном Redis ключ `dashboard:data` так и не наблюдался (нет ни в одной из нескольких БД), но ответы интерфейса нормальные, а задержка при попадании заметно ниже. Во время теста изредка возникал 403 «нет прав доступа» (после 2 случаев снова стабильный 200). Подозрение на различие локальных экземпляров Redis/переменных окружения и продуктива, требуется перепроверка в целевой среде; на выводы теста не влияет (на стабильном участке 0 ошибок).
