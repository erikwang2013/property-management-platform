## 1. Обзор архитектуры системы

Система управления недвижимостью использует многослойную архитектуру «два бэкенда + несколько фронтендов». Админ-панель (admin) и портал жильцов (service) — два независимых проекта webman v2, работающих совместно через общую базу данных MySQL. Фронтенд охватывает Flutter Web (в стиле PC-админки) и мобильные приложения HarmonyOS.

### Цели проектирования

- **Независимое развёртывание**: admin и service запускаются/останавливаются независимо, независимо масштабируются, независимо управляют ключами
- **Общие данные**: используют одну базу данных MySQL, без проблем синхронизации данных
- **Единые стандарты**: оба проекта следуют единым правилам кода, стилю конфигурации и политикам безопасности
- **Web-версия с приоритетом PC**: Flutter Web спроектирован в стиле настольной админ-панели (боковая панель + верхняя панель + область содержимого)

## 2. Многослойная архитектура

```
┌─────────────────────────────────────────────────────────────┐
│                    Слой маршрутизации (Route Layer)           │
│   config/route.php — URL → Controller + привязка middleware  │
├─────────────────────────────────────────────────────────────┤
│                 Слой middleware (Middleware Layer)            │
│   SecurityFilter → RateLimit → ApiVersion → Auth → Permission │
├─────────────────────────────────────────────────────────────┤
│                Слой контроллеров (Controller Layer)           │
│   BaseController → проверка запроса → кодирование ID → бизнес-│
│   логика → форматирование ответа                              │
├─────────────────────────────────────────────────────────────┤
│                    Слой сервисов (Service Layer)              │
│   HashidsService | SnowflakeService | EncryptionService       │
├─────────────────────────────────────────────────────────────┤
│                     Слой моделей (Model Layer)                │
│   Eloquent ORM + encryptable авт.шифрование + scout ES синк   │
├─────────────────────────────────────────────────────────────┤
│                    Слой драйверов (Driver Layer)              │
│   MySQL PDO | Elasticsearch HTTP | Redis                      │
└─────────────────────────────────────────────────────────────┘
```

## 3. Цепочка выполнения middleware

### Админ-панель (admin)
```
Cors → SecurityFilter(проверка метода→405) → RateLimit(ограничение)
  → AdminAuth(проверка JWT) → AdminPermission(проверка RBAC)
    → OperationLog(запись операций) → Controller
```

### Портал жильцов (service)
```
Cors → SecurityFilter(проверка метода→405) → RateLimit(ограничение)
  → ApiVersion(проверка версии) → Controller       # /api/* публичные
  → ServiceAuth(аутентификация JWT владельца) → Controller  # /service/* защищённые
```

### Описание глобальных middleware

| Middleware | Позиция | Обязанности |
|--------|------|------|
| Cors | глобальный, первый | обработка заголовков кросс-доменного доступа |
| SecurityFilter | глобальный | белый список HTTP-методов, блокировка XSS/SQL-инъекций/обхода путей/инъекций команд/CSRF, IP-чёрный список |
| RateLimit | глобальный | скользящее окно Redis (Lua атомарно), по умолчанию 60 раз/мин |
| ApiVersion | маршруты /api | проверка заголовка API-Version, внедрение номера версии |
| AdminAuth | маршруты /admin | проверка JWT Token, внедрение adminId |
| AdminPermission | маршруты /admin | проверка прав RBAC method.path (кэш Redis 60s) |
| OperationLog | маршруты /admin | автоматическая запись операций POST/PUT/DELETE (с определением источника) |
| ServiceAuth | маршруты /service | проверка JWT Token, внедрение ownerId |

## 4. Полный жизненный цикл ID

```
Генерация: SnowflakeService::generate()
      datacenter_id(5bit) + worker_id(5bit) + timestamp(41bit) + sequence(12bit)
      → BIGINT(18) пример: 1750123456789

Хранение: таблицы MySQL management_*
      id BIGINT UNSIGNED NOT NULL (не автоинкремент)
      чувствительные поля cast encryptable → шифрование AES-256-CBC

Передача: HashidsService::encode(bigint) → строка hashid, пример: aB3xK9mW2pQ7rT5v
      все ID-поля в запросах/ответах API единообразно используют hashid

Декодирование: HashidsService::decode(hashid) → BIGINT
      недопустимый hashid вызывает InvalidArgumentException
```

## 5. Многослойное шифрование данных

### Слой передачи (encryption)
- шифрование AES-256-CBC
- клиент шифрует чувствительные данные перед отправкой, сервер расшифровывает после получения
- отдельный ключ `ENCRYPTION_KEY`

### Слой хранения (encryptable)
- механизм `$casts` модели автоматически шифрует/расшифровывает
- чувствительные поля: phone, email, id_card, emergency_contact, emergency_phone
- отдельный ключ `ENCRYPTABLE_KEY`
- запись автоматически шифруется в шифротекст, чтение автоматически расшифровывается

### Слой отображения (маскирование)
- Телефон: `138****1234`
- E-mail: `a***@example.com`
- Удостоверение: `********`
- Экспорт Excel/PDF с автоматическим маскированием

## 6. Аутентификация и права

### Аутентификация JWT
- Алгоритм: HS256
- access_token: срок действия 2 часа
- refresh_token: срок действия 14 дней
- Ограничение параллельности: максимум 3 действующих Token на пользователя, при превышении самый старый Token попадает в чёрный список
- Блокировка аккаунта: 5 неудачных входов подряд — блокировка на 15 минут

### Модель прав RBAC
- Пользователь → роль → право (многие-ко-многим)
- Типы прав: type=1 (меню) / type=2 (кнопка) / type=3 (API)
- Формат идентификатора права: `{method}.{path}`, пример: `get.admin/user`
- Идентификатор супер-администратора: `*` (пропуск всех проверок прав)
- Дерево прав: самоссылка parent_id поддерживает неограниченную вложенность

## 7. Эшелонированная защита (18 уровней)

```
Уровень 1   кликовая капча      → обязательная проверка «человек или робот» при входе/регистрации
Уровень 2   повторное подтверждение пароля → чувствительные операции (удаление/оплата/расторжение договора) требуют пароль
Уровень 3   случайная проверка poster → случайная капча при частых чувствительных операциях
Уровень 4   security-php    → автоматическое сканирование безопасности в цикле запроса
Уровень 5   SecurityFilter  → блокировка XSS/SQL-инъекций/обхода путей/инъекций команд/CSRF
Уровень 6   безопасность передачи → HTTPS + AES-256-CBC
Уровень 7   аутентификация JWT → HS256, 2ч + refresh token
Уровень 8   контроль параллельности → максимум 3 Token на пользователя, превышение — чёрный список
Уровень 9   блокировка аккаунта → 5 неудач подряд — блокировка 15 минут
Уровень 10  авторизация RBAC → контроль прав с точностью method.path
Уровень 11  защита от ограничения частоты → скользящее окно Redis, Lua атомарно
Уровень 12  защита ID → кодировка Hashids, реальный ID не восстановить
Уровень 13  шифрование тела запроса → AES-256-CBC для чувствительных полей
Уровень 14  шифрование хранения → шифрование полей БД encryptable
Уровень 15  маскирование при отображении → телефон/e-mail/удостоверение
Уровень 16  аудит и трассировка → OperationLog полная запись (с автоопределением источника source)
Уровень 17  защита HTTP-заголовков → CSP + X-Permitted-Cross-Domain-Policies
Уровень 18  защита на выходе → PDF водяной знак копирайта (неудаляемый) + маскирование данных Excel
```

## 8. Политика ограничения частоты

Алгоритм скользящего окна на базе Redis Sorted Set, атомарное выполнение скрипта Lua:

| Интерфейс | Ограничение |
|------|------|
| По умолчанию | 60 раз/мин/IP/маршрут |
| POST /api/auth/login | 10 раз/мин |
| POST /api/auth/register | 5 раз/мин |

При превышении возвращается 429 + заголовки `X-RateLimit-Limit/Remaining/Reset/Retry-After`.

## 9. Политика версий API

- Версия управляется заголовком `API-Version` (по умолчанию `v1`), в URL не отражается
- Неподдерживаемая версия возвращает 400
- Контроллеры организованы по версиям: `app/api/{version}/controller/`
- Для новой версии достаточно создать каталог и зарегистрировать его в middleware `ApiVersion`

## 11. Дизайн интернационализации (i18n)

### Структура языковых файлов

Система поддерживает упрощённый китайский (zh_CN) и английский (en), по умолчанию китайский.

**PHP-бэкенд:**
```
resource/translations/
├── zh_CN/
│   └── messages.php    # китайский языковой пакет (42+ ключа перевода)
└── en/
    └── messages.php    # английский языковой пакет
```

Драйвер symfony/translation, конфигурация в `config/translation.php`:
- `locale`: `zh_CN`
- `fallback_locale`: `['zh_CN', 'en']`
- `path`: `resource/translations`

В контроллерах перевод получается через `$this->__('key')`:
```php
return $this->success([], $this->__('create_success'));
return $this->fail($this->__('community.name_required'), 422);
```

Метод `__()` внутри вызывает глобальную функцию webman `trans()`; при отсутствии перевода возвращается сам ключ.

**Flutter Web:**
```
apps/flutter/lib/i18n/
└── messages.dart       # AppTranslations extends GetX Translations
```

Используются GetX `Translations`, 101 ключ перевода. Применение через расширение `.tr`:
```dart
Text('login_btn'.tr)   // китайский: "登 录", английский: "Login"
Text('phone_hint'.tr)  // "请输入手机号" / "Enter phone number"
```

Переключение языка:
```dart
Get.updateLocale(Locale('zh', 'CN'));  // переключить на китайский
Get.updateLocale(Locale('en', 'US'));  // переключить на английский
```

### Категории ключей перевода

| Категория | Примеры ключей PHP | Примеры ключей Flutter |
|------|-----------|---------------|
| Общие | `success`, `fail`, `not_found` | `confirm`, `cancel`, `save` |
| Аутентификация | `auth.login_success`, `auth.*` | `login_btn`, `phone_hint` |
| Комплекс | `community.name_required` | - |
| Платежи | `fee.bill_not_found`, `fee.*` | `fee_management`, `bill_status` |
| Заявки на ремонт | `repair.not_found`, `repair.*` | `repair_submit`, `urgency_normal` |
| Жалобы | `complaint.submit_success` | `complaint_type`, `type_complaint` |
| Личное | - | `profile`, `change_password` |

**HarmonyOS:** используются `resources/base/element/string.json` + `resources/en_US/element/string.json` с квалификаторами ресурсов (реализуется одновременно с созданием проекта HarmonyOS).

## 12. Стратегия тестирования

### Процесс тестирования TDD

Проект следует процессу TDD (разработка через тестирование): красный → зелёный → рефакторинг.

```
RED: сначала пишем тест, наблюдаем падение
  ↓
GREEN: пишем минимальный код, чтобы тест прошёл
  ↓
REFACTOR: чистим код, сохраняя тесты зелёными
```

### Покрытие тестами

| Слой | Фреймворк | Содержание |
|----|---------|---------|
| Базовые сервисы | PHPUnit | генерация Snowflake ID, кодирование/декодирование Hashids, формат ответа |
| База данных | PHPUnit + PDO | проверка структуры таблиц (BIGINT PK, не автоинкремент, префикс management_) |
| Интернационализация | PHPUnit | наличие файлов переводов, согласованность ключей ZH/EN |
| Эндпоинты API | PHPUnit | проверка здоровья, формат ответа |
| Middleware | интеграционные тесты | аутентификация JWT, ограничение частоты, права |

### Запуск тестов

```bash
cd admin && php vendor/bin/phpunit    # админ-панель: 60 tests, 164 assertions
cd service && php vendor/bin/phpunit  # портал жильцов: 18 tests, 45 assertions, 100% pass
```

## 14. Архитектура расширенных функций

### Центр сообщений
шаблон сообщения → генерация уведомления → отправка по нескольким каналам (в приложении/СМС/e-mail/push)

### Рабочий процесс согласования
настройка типа согласования → подача экземпляра → прохождение шагов (одобрить/отклонить) → уведомление следующего согласующего

### Процесс оплаты
создание платёжного заказа → сторонний платёжный сервис → асинхронный колбэк → обновление статуса счёта → запись журнала платежей

### Голосование владельцев
публикация голосования → голосование владельцев (взвешивание по площади) → подсчёт в реальном времени → статистика результатов

### Автоматическая эскалация SLA
сопоставление правил SLA → периодическая проверка превышения срока → автоматическая эскалация → запись штрафа

### Интеллектуальное взыскание
сопоставление стратегии взыскания → обнаружение просрочки → автоматическое создание задач взыскания → выполнение действий взыскания

### Управление патрулированием
выдача задач → отметка GPS на мобильном → загрузка фото → отметка отклонений → статистика завершения

### Управление группой комплексов
связь группа→комплекс → сводные данные по нескольким комплексам (объекты/владельцы/платежи/заявки на ремонт)

| `dateRange` | диапазон дат start_date/end_date |
| `passwordConfirm` | подтверждение паролем password |

## 16. Единый формат ответа

```json

  "code": 0,
  "message": "success",
  "data": {}
}
```

| code | Значение |
|------|------|
| 0 | успех |
