# План расширения (Scaling Plan)

> Copyright (c) 2026 erik <erik@erik.xyz> — https://erik.xyz

Текущее развёртывание — docker-compose на одной машине (MySQL/Redis/Elasticsearch на той же машине, что и приложение, см. `admin/docker-compose.yml`), без HA. В этом документе описаны риски и существующие меры смягчения, дан путь горизонтального расширения, триггерные точки роста данных и рекомендации по тренировкам. Операционная базовая линия (резервирование/восстановление, мониторинг и алерты, ротация журналов) — в [OPS_RUNBOOK.md](OPS_RUNBOOK.md).

## 1. Текущее развёртывание и риски

### 1.1 Текущее состояние

| Компонент | Версия | Описание |
|------|------|------|
| MySQL | 8.0.36 | один экземпляр, данные сохраняются в volume хоста |
| Redis | 7.2-alpine | один экземпляр, кэш/очередь/блокировки |
| Elasticsearch | 8.12.0 | один узел, полнотекстовый поиск scout |
| nginx + webman | — | admin (8787) и service (8788) многопроцессно на одной машине |
| Prometheus + Grafana | — | мониторинг и алерты, на той же машине |

### 1.2 Список рисков

| Риск | Влияние | Вероятность | Последствия |
|------|------|------|------|
| Единая точка отказа (отказ любого middleware) | весь сайт недоступен | низкая | высокие |
| Конкуренция диска/памяти/CPU хоста | медленные запросы, тормоза ES, OOM | средняя (растёт с ростом данных) | средние |
| Необратимое повреждение одного экземпляра MySQL | потеря данных | крайне низкая | крайне высокие |
| Нет резервного ЦОД | отказ уровня ЦОД — полная потеря | крайне низкая | крайне высокие |
| Резервирование/восстановление не тренировано | превышение времени восстановления или сбой | средняя | высокие |

## 2. Существующие меры смягчения (внедрены)

- **Резервирование**: единый скрипт `scripts/backup.sh` (читает соединение из `admin/.env`, по умолчанию mysqldump в контейнере), ежедневное полное резервирование по crontab, по умолчанию хранение 7 дней (настраивается `--keep-days=30`); процесс тренировки восстановления и RPO/RTO — в OPS_RUNBOOK §1 и RECOVERY_RUNBOOK.
- **Мониторинг и алерты**: Prometheus + Grafana + `deploy/monitoring/alerts.yml`, покрытие AppDown / MysqlDown / RedisDown / ElasticsearchDown / QueueBacklog, см. OPS_RUNBOOK §3.
- **Ротация журналов**: журналы контейнеров `max-size 10m`, журналы хоста — ежедневная ротация logrotate с хранением 30 дней, см. OPS_RUNBOOK §4.
- **Прикладной уровень**: постоянные многопроцессные webman, развязка трудоёмких операций задачами очередей, проверка здоровья `/health`.

Вывод: меры выше покрывают «отказ восстанавливаем», **не покрывают «отказ без прерывания»**. Если бизнес не приемлет прерываний, переходить к горизонтальному расширению из §3.

## 3. Путь горизонтального расширения (по приоритету)

Общий принцип расширения: сначала вертикально (добавить CPU/память/диск), затем горизонтально (разнести компоненты); сначала middleware, затем приложение; каждый шаг откатывается независимо.

### 3.1 MySQL ведущий-ведомый + полусинхронизация (первый приоритет)

- Архитектура: ведущая БД (текущий экземпляр) → ведомая (новая машина), включить полусинхронную репликацию (`rpl_semi_sync_master_enabled=1`).
- Расширение чтения: в приложении разделение ведущий/ведомый (включить, когда `config/database.php` поддерживает разделение чтения-записи; иначе сначала только HA ведущий-ведомый).
- Перенос резервирования: скрипт резервирования перевести на ведомую БД, чтобы не нагружать ведущую.
- Версия: ведомая БД должна совпадать по старшей версии с ведущей (сейчас 8.0.36).
- Условия апгрейда: CPU ведущей непрерывно >70%, число соединений близко к max_connections, в журнале медленных запросов резкий рост сканируемых строк.

### 3.2 Redis Sentinel или Cluster (второй приоритет)

- Sentinel (3 узла): при невысоких требованиях к ёмкости — Sentinel, переключение за секунды, клиент должен поддерживать режим `sentinel`.
- Cluster (≥3 ведущих 3 ведомых): объём кэша > памяти одной машины или рост параллелизма записи — Cluster.
- Внимание: очередь и распределённые блокировки зависят от Redis, при смене топологии синхронно менять `config/redis.php` и проверять поведение блокировок/очередей при отказе-переключении.

### 3.3 Отдельный узел Elasticsearch

- У одного узла ES нет реплик — повреждение индекса означает недоступность поиска. Минимум: перенос на отдельную машину + 1 реплика.
- При росте данных разбивать индексы (по бизнес-доменам), отключать ненужные реплики индексов для экономии ресурсов.
- Условия апгрейда: использование кучи >70% непрерывно, отказы записи (`es_rejected_executions` растёт), P95 запросов >1s.

### 3.4 Множественные копии приложения + балансировка нагрузки (в последнюю очередь)

- admin/service по 2+ копии, впереди nginx балансировка нагрузки (round-robin или least_conn).
- Предпосылка: отсутствие состояния (сессии в Redis, нет зависимости от локальной записи файлов; в системе JWT + Redis session, в основном удовлетворяется).
- После этого возможности растут кратно числу копий, затем вернуться к узким местам middleware из §3.1-3.3.

## 4. Триггерные точки роста данных и рекомендации

| Триггер | Порог | Обязательное действие |
|--------|----------|----------|
| Общий объём БД | > 50GB или одна таблица > 50 млн строк | разделение ведущий-ведомый + архивация исторических счетов/журнальных таблиц |
| Медленные запросы | среднесуточно > 10 или один > 2s | добавить индексы, шардирование таблиц, проверить N+1 |
| Соединения MySQL | непрерывно > 80% max_connections | пул соединений + ведущий-ведомый |
| Память Redis | > 70% и продолжает расти | очистка просроченных ключей → Sentinel → Cluster |
| Куча ES | > 70% или отказы записи | отдельный узел + реплики + разбиение индексов |
| CPU | одно ядро непрерывно > 80% и накопление очереди | множественные копии приложения → разнесение middleware |
| Диск | > 80% | очистка копий/журналов, архивация холодных данных |

Рекомендация: сверять таблицу ежемесячно (данные — из панелей Grafana); любой пункт две недели подряд сверх порога — запускать соответствующее расширение.

## 5. Рекомендации по тренировкам расширения

- **Ежеквартально**: тренировка восстановления (см. OPS_RUNBOOK §1.3), проверка RPO/RTO.
- **Ежегодно**: тренировка переключения ведущий-ведомый (тренировать на новой машине, не трогать прод-ведущую): создать ведомую → догнать → переключить → проверить чтение/запись обеих сторон → переключить обратно.
- **После первого расширения**: нагрузочным тестом `scripts/loadtest` прогнать три пути (вход/списки/поиск) и убедиться, что P95 в норме (см. `docs/PERFORMANCE_REPORT_2026-08-16.md`).
- **Протокол тренировок**: каждую тренировку заносить в журнал изменений (CHANGELOG.md), включая: время, пункт, результат, остаточные вопросы.

## 6. Шпаргалка по пути апгрейда

```
Одна машина (текущее состояние)
  ├─ MySQL ведущий-ведомый с полусинхронизацией ← первый приоритет
  ├─ Redis Sentinel/Cluster    ← второй приоритет
  ├─ ES отдельный узел+реплики ← третий приоритет
  └─ Множественные копии приложения+LB ← в последнюю очередь
        ↓
Многомашинное развёртывание (без единой точки; приемлемо прерывание → приемлемы минутные прерывания → переключение за секунды)
```

> При текущем объёме бизнеса расширение не требуется; этот документ — чтобы при «изменении объёма данных/требований к отказам» действовать сразу по нему, без решений на месте.
