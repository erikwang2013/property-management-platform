## 1. Резервное копирование и восстановление базы данных

Админ-панель и портал жильцов используют один экземпляр MySQL и одну БД `management` — копия создаётся один раз. Единая точка входа:

| Имя БД | Скрипт резервирования | Описание |
|---|---|---|
| `management` | `scripts/backup.sh` | читает соединение из `admin/.env` (можно переопределить имя контейнера `--container=`), по умолчанию mysqldump в контейнере |

Вывод: `backups/backup_YYYYMMDD_HHMMSS.sql.gz`, по умолчанию хранение последних 7 дней (настраивается `--keep-days=`).

### 1.1 Полное резервирование

```bash
cd /path/to/property-management-platform
bash scripts/backup.sh
```

### 1.2 Планировщик (crontab)

```cron
# Полное резервирование каждый день в 02:00
0 2 * * * cd /path/to/property-management-platform && bash scripts/backup.sh >> /var/log/pmp-backup.log 2>&1
```

Продовая рекомендация: каталог резервных копий монтировать на отдельный диск/удалённое хранилище и периодически выборочно проверять целостность файлов (`gzip -t`).

### 1.3 Процесс тренировки восстановления (не реже раза в квартал)

1. Выбрать последнюю копию: `ls -t backups/backup_*.sql.gz`
2. Выполнить восстановление в **отдельной среде** (или временной БД): см. [RECOVERY_RUNBOOK.md](RECOVERY_RUNBOOK.md), сценарий A (восстановление в пустую БД) и сценарий B (восстановление на момент времени).
3. Проверка:
   - сравнение строк: `SELECT COUNT(*) FROM management_user;` — совпадает с записью до копирования
   - шифрованные поля расшифровываются нормально: запросить запись с encryptable-полем, значение верное, в журнале нет ошибок decrypt
   - дымовая проверка бизнеса: вход и получение списка работают нормально
4. Записать время и результат тренировки (для оценки RTO).

> Полное руководство по тренировке (восстановление в пустую БД / на момент времени / проверка консистентности / 30-минутный тайм-план) — в [RECOVERY_RUNBOOK.md](RECOVERY_RUNBOOK.md).

### 1.4 Пояснения RPO / RTO

- **RPO (допустимая потеря данных)**: определяется частотой резервирования. Ежедневное полное резервирование → RPO ≤ 24 часа, т.е. максимум потеря данных за последний день. Для меньшего RPO увеличить частоту (например, 2 раза в день) или включить инкрементальное резервирование binlog.
- **RTO (время восстановления)**: зависит от размера БД и скорости восстановления, цель ≤ 1 час (восстановление + проверка + перезапуск сервиса). После каждой тренировки обновлять фактическое измеренное значение.
- Экстренная обработка сбоя восстановления: сначала откатить код приложения, затем повторить с последней доступной копии; если копия повреждена — взять более раннюю и принять больший RPO.

## 2. Управление ключами

Проект зависит от 5 ключей, все в `.env` (admin и service независимы, нельзя использовать один и тот же комплект):

| Переменная | Длина | Назначение |
|---|---|---|
| `ENCRYPTION_KEY` | 32 байта | шифрование API-передачи (config/encryption.php) |
| `ENCRYPTABLE_KEY` | 32 байта | шифрование чувствительных полей БД (плагин encryptable, **нельзя использовать вместе с ENCRYPTION_KEY**) |
| `JWT_SECRET_KEY` | 64+ бита | подпись JWT |
| `HASHIDS_SALT` | — | шифрование/дешифрование ID |
| `HASHIDS_ALT_SALT` | — | запасной ключ шифрования/дешифрования ID |

### 2.1 Генерация ключей

```bash
# Выводит 5 KEY=VALUE в stdout, можно дописывать в .env
php scripts/gen_env_keys.php

# Прямая запись в .env: существующие ключи не перезаписываются, добавляются только отсутствующие
php scripts/gen_env_keys.php --file=.env
```

> Если какой-то ключ в .env всё ещё заполнитель `change-me`, сначала удалите эту строку, затем запускайте (заполнитель считается «уже существующим» и не перезаписывается).

### 2.2 Ротация ключей (encryptable)

```bash
bash scripts/rotate_keys.sh            # по умолчанию работает с .env в текущем каталоге
bash scripts/rotate_keys.sh /path/to/service/.env
```

Скрипт делает автоматически: резервную копию .env → генерирует новый `ENCRYPTABLE_KEY` → добавляет старый ключ в `ENCRYPTION_PREVIOUS_KEYS` (через запятую, последний ротированный — первым) → записывает новый ключ. Затем вручную по подсказке: перезапустить сервис → проверить расшифровку → после подтверждения удалить резервную копию.

**Пояснение `ENCRYPTION_PREVIOUS_KEYS`**: при расшифровке encryptable сначала пробует текущий `ENCRYPTABLE_KEY`, при неудаче последовательно пробует исторические ключи по списку. Поэтому **при ротации старый ключ должен быть добавлен в список до вступления в силу нового ключа**, иначе после перезапуска старые данные не расшифруются (данные не теряются, откат .env восстановит работу). Список только растёт; перед удалением исторических ключей убедиться, что все старые данные перешифрованы.

**Автоматическая миграция данных не выполняется**: после ротации старые данные остаются зашифрованными старым ключом и нормально читаются/пишутся. Если нужно переписать существующие данные новым ключом, выполнить задачу миграции данных отдельно (построчное чтение → запись триггерит повторное шифрование).

### 2.3 Проверка fail-fast при старте

Эти конфигурации проверяются при старте сервиса: при **отсутствии ключа или заполнителе `change-me`** сразу выбрасывается `RuntimeException`, запуск отклоняется (защита от выхода в прод с ключом-заполнителем):

| Конфигурация | Проверяемый ключ |
|---|---|
| `service/config/encryption.php` | `ENCRYPTION_KEY` |
| `service/config/encryptable.php`、`service/config/plugin/erikwang2013/encryptable/app.php` | `ENCRYPTABLE_KEY` |
| `service/config/jwt.php`、`service/config/plugin/erikwang2013/jwt/jwt.php` | `JWT_SECRET_KEY` |

Пример ошибки при старте: `ENCRYPTABLE_KEY 未配置或仍为占位符，请在 .env 中配置 32 字节随机密钥` (ключ ENCRYPTABLE_KEY не настроен или остался заполнителем, задайте в .env 32-байтовый случайный ключ).

**Ежедневный чек-лист**:

1. Развёртывание новой среды: `cp .env.example .env` → удалить строки с `change-me` → `php scripts/gen_env_keys.php --file=.env` → запустить сервис и убедиться в отсутствии ошибок ключей.
2. Плановая ротация: по 2.2, раз в квартал достаточно (обязательного периода нет, при утечке ротировать немедленно).
3. Резервные копии `.env.bak.*` содержат открытые ключи — обращаться как с резервной копией БД (права 600, хранение вне площадки).

## 3. Мониторинг и алерты (Prometheus + Grafana)

Оркестрация в `admin/docker-compose.yml` (добавлены сервисы prometheus / grafana / redis-exporter), конфигурация — в `admin/deploy/monitoring/`:

```bash
cd admin
docker compose up -d prometheus grafana redis-exporter
# Prometheus: http://host:9090   Grafana: http://host:3000
# Первый вход в Grafana: admin / ${GRAFANA_ADMIN_PASSWORD} (по умолчанию change-me-grafana-password)
```

- **Источник данных**: Grafana при старте автоматически настраивает источник Prometheus (provisioning), панели создаются в UI.
- **Правила алертов**: `deploy/monitoring/alerts.yml`, покрытие:
  - `AppDown` (приложение недоступно, эквивалент 5xx всего сайта) — critical
  - `MysqlDown` / `RedisDown` (сбой обнаружения со стороны приложения) — critical
  - `ElasticsearchDown` (сбой сбора нативного `/_prometheus/metrics` ES) + `ElasticsearchHealthYellow` (кластер не зелёный) — critical/warning
  - `QueueBacklog` (накопление в очереди поиска scout `queues:scout_*` >100 записей в течение 10 минут) — warning
- **Внедрение пароля ES**: prometheus читает `ELASTIC_PASSWORD` через compose `secrets` (требуется Docker Compose ≥ 2.24), пароль в конфигурационные файлы не записывается; если не задан — заполнитель change-me, при сбое сбора ES 401 сработает ElasticsearchDown.
- **Перезагрузка правил**: после правки alerts.yml — `curl -X POST localhost:9090/-/reload` (prometheus должен быть запущен с `--web.enable-lifecycle`, по умолчанию без него — перезапуск контейнера).
- **Локальная проверка**: `bash scripts/verify_monitoring.sh` — проверка синтаксиса YAML правил алертов обеих сторон (admin/service), curl `/metrics` обеих сторон (admin:8787 / service:8788) для вывода метрик, загрузка правил Prometheus (9090/9091); если приложение/Prometheus не запущено — для соответствующего пункта выводится SKIP и exit 0.

**Статус**: у admin и service есть эндпоинты `/metrics` (MetricsController, без аутентификации). Middleware MetricsCollector реально накапливает счётчики по `code="all"|"5xx"` (admin выводит `open_admin_http_requests_total`, service — `property_service_http_requests_total`), правила `Http5xxRatio` в alerts.yml обеих сторон (доля 5xx >5% в течение 10 минут) работают напрямую. **Фактическое срабатывание алертов — после развёртывания**: правила готовы, но в реальной среде ещё не проверялись (зависит от `verify_monitoring.sh` и выхода Prometheus в прод).

## 4. Ротация журналов

- **Журналы контейнеров**: во всех сервисах compose настроено `json-file` + `max-size 10m / max-file 3`, дополнительной обработки не требуется.
- **Журналы приложений хоста** (`runtime/*.log`、`service/workerman.log`): используется `admin/deploy/logrotate/pmp-app`:

```bash
sudo cp admin/deploy/logrotate/pmp-app /etc/logrotate.d/pmp-app
# После копирования поправить пути в файле под фактический каталог развёртывания; copytruncate позволяет ротацию без перезапуска webman
sudo logrotate -d /etc/logrotate.d/pmp-app   # пробный запуск для проверки
```

По умолчанию ежедневная ротация, хранение 30 дней, сжатие gzip.

## 5. Дымовая проверка нагрузки после развёртывания

После завершения развёртывания с помощью k6 выполнить дымовую проверку: доступность цепочки входа и ключевых бизнес-интерфейсов (низкая скорость, не нагрузочный тест). Скрипт: `scripts/loadtest/smoke.js` (по умолчанию 2 VU、30s, вход + dashboard, поддерживает переопределение переменными окружения `BASE_URL`/`VUS`/`DURATION`/`TOKEN`).

### 5.1 Локальная дымовая проверка

```bash
cd /path/to/property-management-platform/scripts/loadtest

# Только цепочка входа (token не нужен; 422 ошибка кода подтверждения/429 ограничение частоты — защита сработала, считается доступным)
k6 run -e BASE_URL=http://127.0.0.1:8790 smoke.js

# С бизнес-интерфейсами под авторизацией: на сервере развёртывания выписать JWT для нагрузки (зависит от admin/.env и vendor) и передать
TOKEN=$(php mint-token.php)
k6 run -e BASE_URL=https://admin.example.com -e TOKEN="$TOKEN" smoke.js

# Своя конкуренция/длительность
k6 run -e BASE_URL=https://admin.example.com -e TOKEN="$TOKEN" -e VUS=5 -e DURATION=60s smoke.js
```

Полный нагрузочный тест (три скрипта login + dashboard + fee) по-прежнему через `bash scripts/loadtest/run.sh [BASE_URL] [VUS] [DURATION]`.

### 5.2 Дымовая проверка в CI (ручной запуск GitHub Actions)

Страница Actions репозитория → **Loadtest Smoke** → **Run workflow**:

| Ввод | Обязателен | Описание |
|---|---|---|
| `target_url` | да | адрес тестируемой среды, например `https://admin.example.com` |
| `duration` | нет | длительность дымовой проверки, по умолчанию `30s` |
| `token` | нет | JWT для нагрузки; пусто — только цепочка входа |

Получение token (выполнять в корне репозитория на сервере развёртывания, нужны `admin/.env` и `admin/vendor/`):

```bash
php scripts/loadtest/mint-token.php
```

> Внимание: token — специальный JWT для нагрузки (по умолчанию аккаунт администратора erik), он появится открытым текстом в журнале workflow; выписывайте его под специальный аккаунт для нагрузки; если в проде неудобно раскрывать — используйте локальную дымовую проверку из 5.1.
