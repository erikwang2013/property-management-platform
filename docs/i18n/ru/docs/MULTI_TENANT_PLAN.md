## 1. Инвентаризация текущего состояния

### 1.1 Классификация структуры таблиц (65 таблиц, проверено по docs/install.sql)

| Категория | Таблицы | Описание |
|------|-----|------|
| Глобальные/платформенные | management_admin_user / admin_role / admin_permission / admin_user_role / admin_role_permission、management_system_config、management_operation_log | авторизация, настройки, аудит — естественно платформенный уровень, к арендатору не привязаны |
| Таблицы уровня комплекса | management_community и 40+ бизнес-таблиц, принадлежащих через community_id (building/unit/room/owner/fee_*/repair_order/parking_*/announcement и др.) | через community_id косвенно принадлежат арендатору |
| Таблицы группы | management_group (группа)、management_group_community (группа↔комплекс) | сейчас **необязательная связь**, без семантики арендатора, сводка по объектам через join |
| Платформенные расширения | management_notification_template、management_knowledge_base、management_mall_*、management_face_info и др. | частично платформенный, частично уровень комплекса, требуется уточнение по каждому |
| Легко перепутать | **management_tenant (таблица арендаторов жилья)** | ⚠️ конфликт смыслов: это «арендатор жилья» (измерение room_id/owner_id), **не** SaaS-арендатор |

### 1.2 Цепочка авторизации (админ-панель, проверено по коду)

```
Глобальные middleware: Cors → SecurityFilter → RateLimit
Middleware группы маршрутов: AdminAuth(JWT → $request->adminId) → AdminPermission(RBAC method.path) → OperationLog → Controller
```

- `AdminAuth` уже использует паттерн внедрения в request (`$request->adminId`) — контекст арендатора можно полностью воспроизвести
- `AdminPermission` — платформенный RBAC, **ортогонален** изоляции арендаторов, можно накладывать
- Портал жильцов (service): JWT содержит owner_id, данные естественно ограничены через room_owner → room.community_id, риск межарендаторного доступа низкий

### 1.3 Ключевые выводы

- Готовой SaaS-модели арендаторов нет; имя `management_tenant` занято арендаторами жилья, новому понятию нужно другое имя
- Все контроллеры напрямую используют Eloquent-запросы: нет слоя repository, нет глобальных областей — изоляцию нужно делать на уровне моделей
- В config/database.php одно соединение, но illuminate/database изначально поддерживает несколько connection (задел под эволюцию к отдельным БД)

## 2. Сравнение вариантов и рекомендация

| Вариант | Механизм | Объём переделки | Стоимость эксплуатации | Применимость |
|------|------|--------|----------|------|
| **A. Общая БД + изоляция строк tenant_id (рекомендуется)** | таблица арендаторов + колонка tenant_id в бизнес-таблицах + глобальная область Eloquent | средний (колонки в 2 таблицах + middleware + глобальная область + заполнение существующих данных) | низкая (резервное копирование/миграции единой БД без изменений) | малые и средние объекты недвижимости, <5 млн строк на арендатора |
| B. Отдельные БД (БД на арендатора) | маршрутизация соединений + агрегация между БД | высокая (управление соединениями/отчёты между БД/миграции×N/резервирование×N) | высокая | крупные группы, требования изолированной совместимости |
| C. Гибрид (чувствительные БД отдельно + общая) | комбинация A+B | высокая | высокая | сценарии строгой изоляции платежей/лиц |

**Рекомендация A, эволюционное направление — B.** Причины:

1. Все 65 таблиц в единой БД; модель данных tenant_id в A не мешает будущему разделению БД (грань фильтрации можно сменить со строк на БД — при A идентификатор арендатора уже смоделирован глобально)
2. Бизнес-данные все принадлежат через community_id — tenant_id нужен только в **верхних таблицах**, 40 промежуточных бизнес-таблиц гарантируются путём доступа, колонки добавлять не нужно
3. Обе стороны (admin/service) используют одну модель данных, переделка в A сосредоточена в исполняемом слое админ-панели
4. При текущем развёртывании на одной машине сложность резервирования/миграций B неприемлема

## 3. Проектирование точек изоляции

### 3.1 Модель данных (минимальный набор)

- Новая `management_platform_tenant` (без конфликта с таблицей арендаторов management_tenant): id/name/status/created_at и др.
- В `management_community` добавить `tenant_id BIGINT NOT NULL DEFAULT 0`, индекс `(tenant_id, community_id)`
- В `management_admin_user` добавить `tenant_id BIGINT NOT NULL DEFAULT 0` (0 = платформенный суперадмин)
- Промежуточные бизнес-таблицы (building/room/fee_bill и др., 40 штук) **без новых колонок**, принадлежность через community_id

### 3.2 Три компонента исполняемого слоя

1. **Middleware TenantContext**: в payload JWT добавить утверждение `tenant_id` → `$request->tenantId` (воспроизводит паттерн внедрения AdminAuth); список пропускаемых маршрутов — вход/установка/платформенные (user/role/permission/config)
2. **Глобальная область TenantScope**: повесить глобальную область Eloquent на Community и платформенные бизнес-модели, автофильтрация по `$request->tenantId`; `find()` также ограничивается областью — естественная защита от прямого чтения записи другого арендатора
3. **Явный контекст Tenant::for()**: в планировщиках/очередях/импорте нет HTTP-запроса — обернуть в замыкание с явным указанием арендатора; при отсутствии контекста — **fail-closed** (отказ в запросе), без тихого пропуска без фильтрации

### 3.3 Ключевые пункты тестирования защиты от превышения прав (матрица приёмки)

| Сценарий | Ожидание |
|------|------|
| Админ арендатора A делает list community/building/fee_bill арендатора B | пустой результат или только данные A |
| Админ арендатора A делает find/update/delete одной записи арендатора B (прямой запрос по id) | 403 / пустые данные / отказ |
| Платформенный админ (tenant_id=0) работает с данными разных арендаторов | пропуск (платформенная возможность) |
| Жилец service выполняет операции вне своего комплекса (оплата/ремонт) | отказ (проверка принадлежности community) |
| Планировщик/очередь без указания контекста арендатора | ошибка fail-closed, а не запрос без фильтрации |

## 4. Путь эволюции (поэтапная миграция)

| Шаг | Содержание | Приёмка |
|------|------|------|
| 1. Слой данных | создать таблицу platform_tenant + колонки в community/admin_user + идемпотентная миграция + инициализация арендатора по умолчанию и заполнение существующих данных | каждый community обязательно привязан к арендатору, отчёт по сиротским данным — ноль |
| 2. Исполняемый слой | middleware TenantContext + TenantScope + инструмент Tenant::for() + список пропускаемых маршрутов | регрессия одного арендатора: все 133 теста проходят |
| 3. Пилотные модули | сначала включить изоляцию в четырёх модулях: группа → комплекс → жилец → платежи (счета) | матрица тестов на превышение прав проходит |
| 4. Полное развёртывание | включать по партиям (1-я партия ядро → 2-я вспомогательная → расширения) модуль за модулем | матрица превышения прав всех модулей проходит |
| 5. Эволюция | при данных одного арендатора >5 млн строк или требованиях совместимости оценить разделение БД (вариант B); модель данных A не блокирует | рецензия плана разделения БД |

Стратегия миграции данных: все существующие данные относятся к «арендатору по умолчанию» (создаётся скриптом миграции), бизнес-данные не удаляются и не изменяются; скрипт миграции идемпотентен и повторяем.

## 5. Список рисков

| Риск | Зона влияния | Смягчение / откат |
|------|--------|-------------|
| Большой объём переделки путей запросов 58+17 контроллеров | все бизнес-интерфейсы | глобальная область покрывает ~80% списков/деталей; raw-запросы и массовый импорт через Tenant::for(); серое развёртывание по партиям |
| Глобальная область задевает платформенные запросы (сводка по объектам на дашборде) | дашборд/отчёты | платформенные интерфейсы явно используют Tenant::without() или обход tenant_id=0 |
| Планировщики/очереди без контекста запроса | фоновые задачи напоминаний/SLA/уведомлений | явная обёртка Tenant::for() + fail-closed |
| Ошибки заполнения существующих данных | все существующие данные | идемпотентный скрипт + проверка заполнения + режим сухого прогона |
| Влияние на индексы/производительность | высокочастотные таблицы (fee_bill/room/owner) | составной индекс (tenant_id, community_id); повторная проверка журнала медленных запросов |
| Регрессия 133 тестов | весь объём | после внедрения области сначала полная регрессия, затем пилот |
| Путаница имён (арендатор жилья management_tenant vs SaaS-арендатор) | восприятие разработчиков | новая таблица platform_tenant, явное объявление в документации |
| **План отката** | — | глобальную область можно одним конфигурационным переключателем отключить (возврат к семантике одного арендатора), колонки данных сохраняются, без разрушительных изменений |

## 6. Выводы рецензии

**Рекомендуется сделать сейчас**:
- Общая БД + изоляция строк tenant_id (вариант A), новая таблица `management_platform_tenant`, колонки в community/admin_user
- Middleware TenantContext + глобальная область TenantScope + инструмент Tenant::for()
- Порядок пилота: группа → комплекс → жилец → платежи
- Предварительная зависимость: выполнена — таблицы/колонки/заполнение многопользовательского режима уже встроены в docs/install.sql (объединено 2026-08-16, единая точка создания БД)

**Рекомендуется отложить**:
- Изоляция отдельными БД (B): запускать только при >5 млн строк на арендатора или требованиях совместимости, модель данных уже подготовлена
- Гибридный вариант (C): оценивать, если клиент явно потребует строгую изоляцию платежей/лиц

**Не рекомендуется**:
- Изоляция на уровне схем (в MySQL нет самостоятельной семантики схем, стоимость равна отдельной БД)
- Динамическая маршрутизация по нескольким БД (при развёртывании на одной машине выгоды нет)
- Персонализированные схемы/поля арендатора (YAGNI)
- Переиспользование/переделка management_tenant как SaaS-арендатора (конфликт смыслов, сломает бизнес арендаторов жилья)
