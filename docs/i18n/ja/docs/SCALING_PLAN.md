# スケールアップ計画 (Scaling Plan)

> Copyright (c) 2026 erik <erik@erik.xyz> — https://erik.xyz

現在のデプロイは単機 docker-compose（MySQL/Redis/Elasticsearch がアプリと同機、`admin/docker-compose.yml` 参照）で、HA なし。本ドキュメントはリスクと既存の緩和策を説明し、水平スケールアップのパス、データ量トリガーポイント、訓練の提案を示します。運用ベースライン（バックアップ/復旧、監視アラート、ログローテーション）は [OPS_RUNBOOK.md](OPS_RUNBOOK.md) を参照してください。

## 1. 現在のデプロイとリスク

### 1.1 現状

| コンポーネント | バージョン | 説明 |
|------|------|------|
| MySQL | 8.0.36 | 単一インスタンス、データはホスト機 volume に永続化 |
| Redis | 7.2-alpine | 単一インスタンス、キャッシュ/キュー/ロック |
| Elasticsearch | 8.12.0 | 単一ノード、scout 全文検索 |
| nginx + webman | — | admin（8787）と service（8788）同機マルチプロセス |
| Prometheus + Grafana | — | 監視アラート、同機 |

### 1.2 リスク一覧

| リスク | 影響 | 確率 | 結果 |
|------|------|------|------|
| 単一障害点（いずれかのミドルウェア停止） | 全サイト利用不可 | 低 | 高 |
| ホスト機ディスク/メモリ/CPU の争奪 | スロークエリ、ES 遅延、OOM | 中（データ増加後に上昇） | 中 |
| MySQL 単一インスタンスの復旧不能破損 | データ消失 | 極めて低 | 極めて高 |
| 災害復旧データセンターなし | データセンター級障害で全損 | 極めて低 | 極めて高 |
| バックアップ/復旧が未訓練 | 復旧タイムアウトまたは失敗 | 中 | 高 |

## 2. 既存の緩和策（定着済み）

- **バックアップ**：単一エントリのバックアップスクリプト `scripts/backup.sh`（`admin/.env` から接続情報を読み、デフォルトはコンテナ内 mysqldump）、毎日 crontab フルバックアップ、デフォルト 7 日間保持（`--keep-days=30` で設定可）；復旧訓練フローと RPO/RTO の説明は OPS_RUNBOOK §1 と RECOVERY_RUNBOOK を参照。
- **監視アラート**：Prometheus + Grafana + `deploy/monitoring/alerts.yml`、AppDown / MysqlDown / RedisDown / ElasticsearchDown / QueueBacklog をカバー、OPS_RUNBOOK §3 参照。
- **ログローテーション**：コンテナログ `max-size 10m`、ホスト機ログは logrotate で毎日ローテーション、30 日保持、OPS_RUNBOOK §4 参照。
- **アプリケーション層**：webman マルチプロセス常駐、キューで時間のかかる操作を分離、`/health` ヘルスチェック。

結論：上記の緩和策は「障害から復旧できる」をカバーし、「障害で中断しない」はカバーしない。業務上中断が許容できない場合、§3 の水平スケールアップに進む必要がある。

## 3. 水平スケールアップパス（優先度順）

スケールアップの総原則：まず縦方向（CPU/メモリ/ディスク追加）→ 次に横方向（コンポーネント分離）、まずミドルウェア → 次にアプリ、各ステップは独立してロールバック可能。

### 3.1 MySQL マスター/スレーブ + セミシンク（第一優先）

- アーキテクチャ：マスター（既存インスタンス）→ スレーブ（新マシン）、セミシンクレプリケーション有効化（`rpl_semi_sync_master_enabled=1`）。
- 読み取り拡張：アプリでマスター/スレーブ分離を設定（`config/database.php` が読み書き分離対応なら有効化；それ以外はまずマスター/スレーブ HA のみ）。
- バックアップ移行：バックアップスクリプトをスレーブ向けに変更し、マスターへのバックアップ負荷を回避。
- バージョン：スレーブはマスターとメジャーバージョン一致が必要（現在 8.0.36）。
- アップグレード条件：マスターマシン CPU が継続 >70%、接続数が max_connections に接近、スロークエリログでスキャン行数が急増。

### 3.2 Redis センチネルまたはクラスター（第二優先）

- センチネル（3 ノード）：容量要件が高くない場合はセンチネルを選択、切替は秒単位、クライアントが `sentinel` モード対応が必要。
- クラスター（≥3 マスター 3 スレーブ）：キャッシュ量が単機メモリ超過、または書き込み並列が上昇した場合にクラスターを選択。
- 注意：キューと分散ロックは Redis に依存するため、トポロジー変更時は `config/redis.php` も同時に変更し、障害移転時のロック/キューの挙動を検証する。

### 3.3 Elasticsearch 独立ノード

- 単一ノード ES はレプリカなしで、インデックス破損で検索が即利用不可。少なくとも独立マシン + レプリカ 1 に移行。
- データ量増加後はインデックスを分割（業務ドメイン毎）、不要なインデックスのレプリカを閉じてリソースを制御。
- アップグレード条件：ヒープメモリ使用 >70% 継続、書き込み拒否（`es_rejected_executions` 上昇）、クエリ P95 が 1 秒超過。

### 3.4 アプリ複数レプリカ + ロードバランサ（最後）

- admin/service を各 2+ レプリカ起動し、前段 nginx でロードバランシング（ラウンドロビンまたは least_conn）。
- 前提条件：ステートレス（セッションは Redis、ローカルファイル書き込み依存なし；本システムは JWT + Redis session で概ね満たす）。
- その後レプリカ数倍で処理能力が倍増し、再度 §3.1-3.3 のミドルウェアボトルネックに戻る。

## 4. データ量増加のトリガーポイントと提案

| トリガーポイント | 閾値の提案 | 必須アクション |
|--------|----------|----------|
| データベース総量 | > 50GB または単テーブル > 5000 万行 | マスター/スレーブ分割 + 履歴請求書/ログテーブルのアーカイブ |
| スロークエリ | 日平均スロークエリ > 10 件または 1 件 > 2s | インデックス追加、テーブル分割、N+1 調査 |
| MySQL 接続 | 継続 > 80% max_connections | 接続プール + マスター/スレーブ |
| Redis メモリ | > 70% かつ継続増加 | 期限切れキー掃除 → センチネル → クラスター |
| ES ヒープメモリ | > 70% または書き込み拒否 | 独立ノード + レプリカ + インデックス分割 |
| CPU | シングルコア継続 > 80% かつキュー滞留 | アプリ複数レプリカ → ミドルウェア分割 |
| ディスク | > 80% | バックアップ/ログの掃除、コールドデータのアーカイブ |

提案：毎月上表を一度確認（データは Grafana パネルから取得可能）、いずれかの項目が 2 週間連続で閾値超過なら対応するスケールアップを開始。

## 5. スケールアップ訓練の提案

- **四半期に 1 回**：復旧訓練（OPS_RUNBOOK §1.3 参照）、RPO/RTO 達成を検証。
- **年に 1 回**：マスター/スレーブ切替訓練（新マシンで訓練、本番マスターに触れない）：スレーブ構築 → 追い付き → 切替 → 両端読み書き検証 → 切替戻し。
- **初回スケールアップ後**：`scripts/loadtest` で 3 パス（ログイン/一覧/検索）を負荷試験し P95 達成を確認（`docs/PERFORMANCE_REPORT_2026-08-16.md` 参照）。
- **訓練記録**：毎回の訓練を変更ログ（CHANGELOG.md）に記録：日時、訓練項目、結果、残課題。

## 6. アップグレードパス早見表

```
単機（現状）
  ├─ MySQL マスター/スレーブセミシンク      ← 第一優先
  ├─ Redis センチネル/クラスター    ← 第二優先
  ├─ ES 独立ノード+レプリカ       ← 第三優先
  └─ アプリ複数レプリカ+LB          ← 最後
        ↓
多機デプロイ（単一障害点なし、障害中断許容 → 分単位中断許容 → 秒単位切替）
```

> 現在の業務量ではスケールアップ不要。本ドキュメントは「データ量/障害要件が変化した時」にそのまま実施できるようにするためのもので、場当たり的な判断を避ける。
