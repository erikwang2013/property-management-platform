## 1. テスト環境と方法

| 項目 | 値 |
|---|---|
| アプリ | webman v2（PHP 8.3、32 workers）、admin + service のデュアルアプリ |
| 被験インスタンス | admin 独立ポート 8790（`SERVER_LISTEN=http://0.0.0.0:8790`） |
| ツール | k6 v0.51.0（本機に wrk/ab/hey なし）、スクリプトは `scripts/loadtest/` |
| 負荷試験対象 | ログイン（/api/auth/login）、ダッシュボード（/admin/dashboard）、料金支払い一覧（/admin/fee-payment） |
| 認証 | dashboard/fee は `scripts/loadtest/mint-token.php` で JWT 発行（認証コードをバイパス、`sub=21000000000000100`）；ログインスクリプトは無効な認証コードでチェーンを探索 |
| データ | 単機直結 127.0.0.1、ゲートウェイ/CDN 経由なし；MySQL/Redis はアプリと同機 |

スクリプトエントリ：`bash scripts/loadtest/run.sh [BASE_URL] [VUS] [DURATION]`（k6 が PATH にある必要あり）。
ログインスクリプト説明：ログインは認証コード + レート制限（10 回/分/IP）の二重保護で、セキュリティ設計上のものであり、高並列負荷試験はできず、すべきでもない；login.js は 1 VU / 8 リクエストの低レートでチェーン遅延を探索し、期待される応答は 422（認証コードエラー）または 429（レート制限）で、いずれも防御が正常に機能していることを示す。

## 2. 負荷試験結果

### 20 VU / 30s（基準負荷）

| インターフェース | リクエスト数 | スループット | avg | p90 | p95 | max | 失敗率 |
|---|---|---|---|---|---|---|---|
| login（1 VU × 8 回） | 8 | 14.4/s | 68.6ms | 154ms | 207.8ms | 261ms | 0% |
| dashboard | 6863 | 227.9/s | 86.0ms | 151ms | 189.5ms | 1.37s | 0% |
| fee-payment | 5944 | 197.2/s | 99.3ms | 178ms | 220.0ms | 704ms | 0% |

### 50 VU / 30s（負荷増強）

| インターフェース | リクエスト数 | スループット | avg | p95 | max | 失敗率 |
|---|---|---|---|---|---|---|
| login（1 VU × 8 回） | 8 | 18.7/s | 52.1ms | 173ms | 243.8ms | 0% |
| dashboard | 6902 | 226.9/s | 212.7ms | 544.0ms | 1.99s | 0% |
| fee-payment | 7525 | 247.4/s | 195.7ms | 514.2ms | 2.0s | 0% |

（50 VU で p95 > 500ms 閾値となり、k6 が閾値超過と判定して終了したが、リクエスト失敗 0%、非 200 も 0。）

### 結論

- 全インターフェースが 20 VU で失敗 0、p95 < 220ms、健全。
- **スループットボトルネックは約 230–250 rps**：20 VU → 50 VU でスループットは上がらず横ばい（dashboard 227.9 → 226.9、fee 197 → 247）なのに、p95 遅延は倍増（~190ms → ~540ms）。単機 32 worker で worker 当たり約 7–8 rps は、PHP 全チェーン（MySQL クエリ、Redis キャッシュ往復含む）のシングルコア処理上限の特性であり、接続枯渇ではない（失敗リクエストなし）。
- 提案：単機でこの規模は十分（約 2 千万リクエスト/日）；より高いスループットが必要なら、まず水平にインスタンス追加、次に各インターフェースの SQL とキャッシュヒットを調査（下記参照）。

## 3. スロークエリ審査

- 料金テーブル `erik_fee_bill` / `erik_fee_payment` のインデックスは整備済み（paid_at、bill_id、owner_id、payment_number 等）、コアクエリは全てインデックス利用可能。
- 発見点：料金一覧の `payment_number like %kw%` あいまい検索（前方ワイルドカード）はインデックスを利用できず、データ量が増えると全テーブルスキャンに退化する。低頻度の管理画面検索のため、現状は対応しない；データ量増加後は逆インデックスまたは接頭辞インデックスに変更可能。
- **MySQL slow_query_log が OFF**：有効化して `long_query_time=1` を設定することを推奨し、実 SQL のスローを継続観察（負荷試験からの推測ではなく）。本番実行：
  ```sql
  SET GLOBAL slow_query_log = ON;
  SET GLOBAL long_query_time = 1;
  ```
- ダッシュボード集計：キャッシュ再構築のたびに約 8 つの COUNT 集計 + 30 日分のグループ統計を実行、再構築 1 回は秒単位のコストで、Redis 5 分キャッシュで吸収される（下記参照）、ホットパスではない。

## 4. Redis キャッシュ再調査

- ダッシュボードキャッシュ `dashboard:data`：`setex 300`、ヒット時 ~10ms、ミス時再構築は秒単位。**問題：書き込み操作による失効ロジックが一切ない**ため、データ変更後最大 5 分間陳腐化。料金/不動産の書き込み API でこのキーを削除することを推奨（一行 `del dashboard:data`）。
- **キャッシュスタンピード保護なし**：キー失効の瞬間に 32 worker が同時再構築（8 集計クエリを重複実行）。データ量増加後は簡易ミューテックス（例：`set nx ex` ロック + ダブルチェック）を推奨。
- 権限キャッシュ `perm:{adminId}` 60s、挙動は正常。
- 残調査項目：本機 Redis では `dashboard:data` キーが最後まで観察されなかった（複数 db 全てなし）が、API 応答は正常でヒット時遅延が明らかに低い。負荷試験中に偶発的な 403「権限なし」（2 回発生後に安定 200）。本機の複数 Redis インスタンス/環境変数設定と本番の差異が疑われ、対象環境で再確認が必要。負荷試験結論には影響なし（安定区間は失敗 0）。
