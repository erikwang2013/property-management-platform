# क्षमता विस्तार योजना (Scaling Plan)

> Copyright (c) 2026 erik <erik@erik.xyz> — https://erik.xyz

वर्तमान तैनाती सिंगल-मशीन docker-compose है (MySQL/Redis/Elasticsearch एप्लिकेशन के साथ एक ही मशीन पर, देखें `admin/docker-compose.yml`), कोई HA नहीं। यह दस्तावेज़ जोखिमों और मौजूदा शमन उपायों की व्याख्या करता है, क्षैतिज विस्तार पथ, डेटा मात्रा ट्रिगर बिंदु और अभ्यास सुझाव देता है। संचालन आधार रेखा (बैकअप/पुनर्स्थापना、मॉनिटरिंग अलर्ट、लॉग रोटेशन) के लिए [OPS_RUNBOOK.md](OPS_RUNBOOK.md) देखें।

## 2. मौजूदा शमन उपाय (लागू)

- **बैकअप**: सिंगल-एंट्री बैकअप स्क्रिप्ट `scripts/backup.sh` (कनेक्शन `admin/.env` से पढ़ता है, डिफ़ॉल्ट कंटेनर में mysqldump), दैनिक crontab पूर्ण बैकअप, डिफ़ॉल्ट 7 दिन रखता है (`--keep-days=30` कॉन्फ़िगर करने योग्य); पुनर्स्थापना अभ्यास प्रवाह और RPO/RTO विवरण OPS_RUNBOOK §1 और RECOVERY_RUNBOOK में।
- **मॉनिटरिंग अलर्ट**: Prometheus + Grafana + `deploy/monitoring/alerts.yml`, AppDown / MysqlDown / RedisDown / ElasticsearchDown / QueueBacklog कवर करता है, OPS_RUNBOOK §3 देखें।
- **लॉग रोटेशन**: कंटेनर लॉग `max-size 10m`, होस्ट मशीन लॉग logrotate दैनिक रोटेशन 30 दिन रखता है, OPS_RUNBOOK §4 देखें।
- **एप्लिकेशन परत**: webman मल्टी-प्रोसेस स्थायी, कतार कार्य समय लेने वाले संचालन को अलग करते हैं, `/health` हेल्थ चेक।

निष्कर्ष: उपरोक्त शमन उपाय "विफलता के बाद पुनर्स्थापना" कवर करते हैं, **"विफलता के बिना निरंतरता" कवर नहीं करते**। यदि व्यवसाय के लिए रुकावट अस्वीकार्य है, तो §3 के क्षैतिज विस्तार की आवश्यकता है।

## 3. क्षैतिज विस्तार पथ (प्राथमिकता क्रम में)

विस्तार के मूल सिद्धांत: पहले ऊर्ध्वाधर (CPU/मेमोरी/डिस्क बढ़ाएं) फिर क्षैतिज (घटक अलग करें), पहले मिडलवेयर फिर एप्लिकेशन, प्रत्येक चरण स्वतंत्र रूप से रोलबैक योग्य।

### 3.1 MySQL मास्टर-स्लेव + सेमी-सिंक (पहली प्राथमिकता)

- आर्किटेक्चर: मास्टर (मौजूदा इंस्टेंस) → स्लेव (नई मशीन), सेमी-सिंक्रोनस रेप्लिकेशन सक्षम (`rpl_semi_sync_master_enabled=1`)।
- रीड विस्तार: एप्लिकेशन में मास्टर-स्लेव अलगाव कॉन्फ़िगर करें (`config/database.php` रीड-राइट अलगाव समर्थित होने पर सक्षम करें; अन्यथा पहले केवल मास्टर-स्लेव HA)।
- बैकअप माइग्रेशन: बैकअप स्क्रिप्ट स्लेव की ओर इंगित करें, मास्टर पर बैकअप का दबाव बचें।
- संस्करण: स्लेव का मेजर संस्करण मास्टर के समान होना चाहिए (वर्तमान 8.0.36)।
- अपग्रेड शर्तें: मास्टर CPU लगातार >70%、कनेक्शन संख्या max_connections के करीब、धीमी क्वेरी लॉग में स्कैन की गई पंक्तियों में तेज वृद्धि।

### 3.2 Redis सेंटिनल या क्लस्टर (दूसरी प्राथमिकता)

- सेंटिनल (3 नोड): क्षमता आवश्यकता अधिक न होने पर सेंटिनल चुनें, स्विच सेकंड-स्तरीय, क्लाइंट को `sentinel` मोड समर्थित करना चाहिए।
- Cluster (≥3 मास्टर 3 स्लेव): कैश मात्रा > सिंगल मशीन मेमोरी、या लेखन समवर्ती बढ़ने पर Cluster चुनें।
- ध्यान दें: कतार और वितरित लॉक Redis पर निर्भर हैं, टोपोलॉजी बदलते समय `config/redis.php` भी बदलना होगा और फेलओवर के दौरान लॉक/कतार के व्यवहार को सत्यापित करना होगा।

### 3.3 Elasticsearch स्वतंत्र नोड

- सिंगल नोड ES में कोई रेप्लिका नहीं है, इंडेक्स क्षतिग्रस्त होने पर खोज अनुपलब्ध। कम से कम स्वतंत्र मशीन + 1 रेप्लिका पर माइग्रेट करें।
- डेटा मात्रा बढ़ने के बाद इंडेक्स विभाजित करें (व्यवसाय डोमेन के अनुसार), अनावश्यक इंडेक्स रेप्लिका बंद करें ताकि संसाधन नियंत्रित रहें।
- अपग्रेड शर्तें: हीप मेमोरी उपयोग >70% लगातार、लेखन अस्वीकृति (`es_rejected_executions` बढ़ना)、क्वेरी P95 1s से अधिक।

### 3.4 एप्लिकेशन मल्टी-रेप्लिका + लोड बैलेंसर (अंतिम)

- admin/service प्रत्येक 2+ रेप्लिका, आगे nginx लोड बैलेंसिंग (राउंड-रॉबिन या least_conn)।
- पूर्व शर्तें: स्टेटलेस (सत्र Redis में、कोई स्थानीय फ़ाइल लेखन निर्भरता नहीं; यह सिस्टम JWT + Redis session, मूल रूप से संतुष्ट)।
- उसके बाद रेप्लिका संख्या के अनुसार प्रसंस्करण क्षमता दोगुनी, फिर §3.1-3.3 के मिडलवेयर बाधाओं पर लौटें।

## 4. डेटा मात्रा वृद्धि ट्रिगर बिंदु और सुझाव

| ट्रिगर बिंदु | थ्रेशोल्ड सुझाव | अनिवार्य कार्रवाई |
|--------|----------|----------|
| डेटाबेस कुल मात्रा | > 50GB या सिंगल टेबल > 50 मिलियन पंक्तियाँ | मास्टर-स्लेव विभाजन + पुराने बिल/लॉग टेबल संग्रह |
| धीमी क्वेरी | दैनिक औसत धीमी क्वेरी > 10 या एकल > 2s | इंडेक्स जोड़ें、टेबल विभाजन、N+1 जांचें |
| MySQL कनेक्शन | लगातार > 80% max_connections | कनेक्शन पूल + मास्टर-स्लेव |
| Redis मेमोरी | > 70% और लगातार बढ़ रही | समाप्त कुंजियाँ साफ़ करें → सेंटिनल → Cluster |
| ES हीप मेमोरी | > 70% या लेखन अस्वीकृति | स्वतंत्र नोड + रेप्लिका + इंडेक्स विभाजन |
| CPU | सिंगल कोर लगातार > 80% और कतार संचय | एप्लिकेशन मल्टी-रेप्लिका → मिडलवेयर विभाजन |
| डिस्क | > 80% | बैकअप/लॉग साफ़ करें, कोल्ड डेटा संग्रह करें |

सुझाव: हर महीने उपरोक्त तालिका की जांच करें (डेटा Grafana पैनल से लिया जा सकता है), कोई भी आइटम लगातार दो सप्ताह थ्रेशोल्ड पार करे तो संबंधित विस्तार शुरू करें।

## 5. क्षमता विस्तार अभ्यास सुझाव

- **हर तिमाही एक बार**: पुनर्स्थापना अभ्यास (OPS_RUNBOOK §1.3 देखें), RPO/RTO मानक पूर्ति सत्यापित करें।
- **हर साल एक बार**: मास्टर-स्लेव स्विच अभ्यास (नई मशीन पर अभ्यास करें, प्रोडक्शन मास्टर को न छुएं): स्लेव बनाएं → बराबरी करें → स्विच करें → दोनों ओर रीड-राइट सत्यापित करें → वापस स्विच करें।
- **पहले विस्तार के बाद**: `scripts/loadtest` से तीन पथों (लॉगिन/सूची/खोज) का दबाव परीक्षण करें, P95 मानक पूर्ति की पुष्टि करें (`docs/PERFORMANCE_REPORT_2026-08-16.md` देखें)।
- **अभ्यास रिकॉर्ड**: हर अभ्यास परिवर्तन लॉग (CHANGELOG.md) में दर्ज करें, इसमें शामिल: समय、अभ्यास आइटम、परिणाम、शेष समस्याएँ।

## 6. अपग्रेड पथ त्वरित संदर्भ

```
सिंगल मशीन (वर्तमान स्थिति)
  ├─ MySQL मास्टर-स्लेव सेमी-सिंक      ← पहली प्राथमिकता
  ├─ Redis सेंटिनल/Cluster    ← दूसरी प्राथमिकता
  ├─ ES स्वतंत्र नोड+रेप्लिका       ← तीसरी प्राथमिकता
  └─ एप्लिकेशन मल्टी-रेप्लिका+LB          ← अंतिम
        ↓
मल्टी-मशीन तैनाती (कोई सिंगल पॉइंट नहीं, विफलता रुकावट स्वीकार्य → मिनट-स्तरीय रुकावट स्वीकार्य → सेकंड-स्तरीय स्विच)
```

> वर्तमान व्यवसाय मात्रा में विस्तार की आवश्यकता नहीं, यह दस्तावेज़ "डेटा मात्रा/विफलता आवश्यकताओं में बदलाव पर" सीधे अनुसरण करने के लिए है, स्थिति में निर्णय से बचने के लिए।
