### 1.2 प्राधिकरण श्रृंखला (admin पोर्टल, कोड से सत्यापित)

```
वैश्विक मिडलवेयर: Cors → SecurityFilter → RateLimit
रूट समूह मिडलवेयर: AdminAuth(JWT → $request->adminId) → AdminPermission(RBAC method.path) → OperationLog → Controller
```

- `AdminAuth` ने अनुरोध इंजेक्शन पैटर्न स्थापित किया है (`$request->adminId`), टेनेंट संदर्भ पूरी तरह से प्रतिकृति योग्य
- `AdminPermission` प्लेटफ़ॉर्म-स्तरीय RBAC है, टेनेंट अलगाव के साथ **ऑर्थोगोनल**, सुपरइम्पोज़ किया जा सकता है
- service मालिक पोर्टल: JWT owner_id रखता है, डेटा room_owner → room.community_id से स्वाभाविक रूप से सीमित, क्रॉस-टेनेंट जोखिम कम

### 1.3 मुख्य निष्कर्ष

- कोई मौजूदा SaaS टेनेंट मॉडल नहीं; `erik_tenant` नाम किरायेदार द्वारा लिया जा चुका है, नई अवधारणा के लिए नाम से बचना अनिवार्य
- सभी कंट्रोलर सीधे Eloquent क्वेरी करते हैं, कोई repository परत नहीं、कोई वैश्विक scope नहीं — अलगाव सुधार मॉडल परत पर करना होगा
- config/database.php सिंगल कनेक्शन, लेकिन illuminate/database मूल रूप से मल्टी-कनेक्शन समर्थित करता है (स्वतंत्र डेटाबेस विकास के लिए आरक्षित)

| योजना | तंत्र | सुधार मात्रा | संचालन लागत | उपयुक्तता |
|------|------|--------|----------|------|
| **A. साझा डेटाबेस + tenant_id पंक्ति अलगाव (अनुशंसित)** | टेनेंट टेबल + व्यवसाय टेबल tenant_id कॉलम + Eloquent वैश्विक scope फ़िल्टर | मध्यम (2 टेबल कॉलम + मिडलवेयर + वैश्विक scope + मौजूदा डेटा बैकफिल) | कम (सिंगल डेटाबेस बैकअप/माइग्रेशन अपरिवर्तित) | छोटे-मध्यम संपत्ति, सिंगल टेनेंट <5 मिलियन पंक्तियाँ |

| C. हाइब्रिड (संवेदनशील डेटाबेस स्वतंत्र + साझा) | A+B संयोजन | उच्च | उच्च | भुगतान/चेहरा जैसे मजबूत अलगाव परिदृश्य |

**A अनुशंसित, B विकास दिशा।** कारण:

1. मौजूदा 65 टेबल एक ही डेटाबेस में एकीकृत, A का tenant_id डेटा मॉडल भविष्य में डेटाबेस विभाजन को बाधित नहीं करता (फ़िल्टर ग्रैन्युलैरिटी पंक्ति से डेटाबेस में बदल सकती है, A योजना में टेनेंट ID पहले से वैश्विक रूप से मॉडल किया गया)
2. व्यवसाय डेटा सभी community_id से संबद्ध, tenant_id केवल **शीर्ष-स्तरीय टेबल** में जोड़ना होगा, बीच की 40 व्यवसाय टेबल एक्सेस पथ से सुरक्षित, हर टेबल में कॉलम जोड़ने से बचा जाता है
3. दोनों पोर्टल (admin/service) एक ही डेटा मॉडल साझा करते हैं, A का सुधार admin पोर्टल के रनटाइम परत पर केंद्रित
4. सिंगल-मशीन तैनाती की वर्तमान स्थिति में B की बैकअप/माइग्रेशन जटिलता असहनीय है

## 3. अलगाव बिंदु डिज़ाइन

### 3.1 डेटा मॉडल (न्यूनतम सेट)

- नई `erik_platform_tenant` (किरायेदार टेबल erik_tenant से टकराव से बचने के लिए): id/name/status/created_at आदि
- `erik_community` में `tenant_id BIGINT NOT NULL DEFAULT 0` जोड़ें, इंडेक्स `(tenant_id, community_id)`
- `erik_admin_user` में `tenant_id BIGINT NOT NULL DEFAULT 0` जोड़ें (0 = प्लेटफ़ॉर्म सुपर एडमिन)
- व्यवसाय मध्यवर्ती टेबल (building/room/fee_bill आदि 40 टेबल) में **कॉलम न जोड़ें**, community_id से संबद्ध

### 3.2 रनटाइम परत तीन-पीस सेट

1. **TenantContext मिडलवेयर**: JWT payload में `tenant_id` दावा → `$request->tenantId` (AdminAuth इंजेक्शन पैटर्न की प्रतिकृति); लॉगिन/इंस्टॉल/प्लेटफ़ॉर्म-स्तरीय रूट (user/role/permission/config) अनुमति सूची
2. **TenantScope वैश्विक scope**: Community और प्लेटफ़ॉर्म-स्तरीय व्यवसाय मॉडल पर Eloquent वैश्विक scope लगाएं, `$request->tenantId` के अनुसार स्वतः फ़िल्टर; `find()` भी scope से सीमित, स्वाभाविक रूप से क्रॉस-टेनेंट सिंगल-रिकॉर्ड सीधी क्वेरी रोकता है
3. **Tenant::for() स्पष्ट संदर्भ**: शेड्यूल्ड टास्क/कतार/इम्पोर्ट में कोई HTTP अनुरोध नहीं, क्लोजर से स्पष्ट टेनेंट निर्दिष्ट करें; संदर्भ अनुपलब्ध होने पर **fail-closed** (क्वेरी अस्वीकार), बिना फ़िल्टर मौन अनुमति नहीं

### 3.3 अधिकार उल्लंघन सुरक्षा परीक्षण बिंदु (स्वीकृति मैट्रिक्स)

| मामला | अपेक्षा |
|------|------|
| टेनेंट A एडमिन टेनेंट B का community/building/fee_bill सूचीबद्ध करता है | खाली या केवल A डेटा लौटे |
| टेनेंट A एडमिन टेनेंट B का एकल रिकॉर्ड find/update/delete करता है (सीधी id क्वेरी) | 403 / खाली डेटा / अस्वीकार |
| प्लेटफ़ॉर्म एडमिन (tenant_id=0) क्रॉस-टेनेंट संचालन | अनुमति (प्लेटफ़ॉर्म-स्तरीय क्षमता) |
| service मालिक क्रॉस-समुदाय संचालन (भुगतान/मरम्मत) | अस्वीकार (community संबद्धता सत्यापन) |
| शेड्यूल्ड टास्क/कतार में टेनेंट संदर्भ निर्दिष्ट नहीं | fail-closed त्रुटि, बिना फ़िल्टर नहीं |

## 4. विकास पथ (चरणबद्ध माइग्रेशन)

| चरण | सामग्री | स्वीकृति |
|------|------|------|
| 1. डेटा परत | platform_tenant टेबल बनाएं + community/admin_user कॉलम जोड़ें + आइडेम्पोटेंट माइग्रेशन + डिफ़ॉल्ट टेनेंट आरंभीकरण और मौजूदा डेटा बैकफिल | हर community अनिवार्य रूप से टेनेंट से जुड़ा, अनाथ डेटा रिपोर्ट शून्य |
| 2. रनटाइम परत | TenantContext मिडलवेयर + TenantScope + Tenant::for() उपकरण + रूट अनुमति सूची | सिंगल-टेनेंट रिग्रेशन: पूरे 133 परीक्षण पास |

| 4. पूर्ण विस्तार | बैच के अनुसार (बैच 1 मुख्य → बैच 2 सहायक → विस्तार मॉड्यूल) मॉड्यूल-दर-मॉड्यूल सक्षम | सभी मॉड्यूल अधिकार उल्लंघन मैट्रिक्स पास |
| 5. विकास | सिंगल टेनेंट डेटा >5 मिलियन पंक्तियाँ या अनुपालन आवश्यकता होने पर डेटाबेस विभाजन (योजना B) मूल्यांकन, A का डेटा मॉडल बाधित नहीं करता | विभाजन योजना समीक्षा |

डेटा माइग्रेशन रणनीति: मौजूदा डेटा सभी "डिफ़ॉल्ट टेनेंट" में (माइग्रेशन स्क्रिप्ट बनाती है), न हटाएं न बदलें व्यवसाय डेटा; माइग्रेशन स्क्रिप्ट आइडेम्पोटेंट, बार-बार निष्पादन योग्य।

## 6. समीक्षा निष्कर्ष

**तुरंत करने की सलाह**:
- साझा डेटाबेस + tenant_id पंक्ति अलगाव (योजना A), नई `erik_platform_tenant` टेबल, community/admin_user कॉलम जोड़ें
- TenantContext मिडलवेयर + TenantScope वैश्विक scope + Tenant::for() उपकरण
- पायलट क्रम: समूह → समुदाय → मालिक → शुल्क
- पूर्व निर्भरता: पूर्ण — मल्टी-टेनेंट टेबल/कॉलम/बैकफिल docs/install.sql में इनलाइन किए गए (2026-08-16 मर्ज लागू, एकल डेटाबेस निर्माण प्रवेश)

**धीरे करने की सलाह**:
- स्वतंत्र डेटाबेस अलगाव (B): केवल सिंगल टेनेंट >5 मिलियन पंक्तियाँ या अनुपालन आवश्यकता पर शुरू, डेटा मॉडल पहले से आरक्षित
- हाइब्रिड योजना (C): भुगतान/चेहरा जैसे मजबूत अलगाव परिदृश्य पर ग्राहक स्पष्ट रूप से मांग करे तो मूल्यांकन

**न करने की सलाह**:
- Schema-स्तरीय अलगाव (MySQL में स्वतंत्र schema अर्थ नहीं, लागत स्वतंत्र डेटाबेस के बराबर)
- डायनामिक मल्टी-डेटाबेस रूटिंग (सिंगल-मशीन तैनाती में कोई लाभ नहीं)
- टेनेंट-स्तरीय वैयक्तिकृत schema/फ़ील्ड (YAGNI)
- erik_tenant किरायेदार टेबल का पुनः उपयोग/सुधार SaaS टेनेंट के रूप में (अर्थ टकराव, किरायेदार व्यवसाय बाधित)
