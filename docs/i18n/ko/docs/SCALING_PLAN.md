# 확장 대비 방안 (Scaling Plan)

> Copyright (c) 2026 erik <erik@erik.xyz> — https://erik.xyz

현재 배포는 단일 머신 docker-compose（MySQL/Redis/Elasticsearch와 애플리케이션 동일 머신, `admin/docker-compose.yml` 참조）, HA 없음. 본 문서는 리스크와 기존 완화를 설명하고, 수평 확장 경로, 데이터량 트리거 포인트와 훈련 제안을 제시합니다. 운영 베이스라인（백업/복구, 모니터링 알림, 로그 로테이션）은 [OPS_RUNBOOK.md](OPS_RUNBOOK.md) 참조.

## 2. 기존 완화（구축 완료）

- **백업**: 단일 진입점 백업 스크립트 `scripts/backup.sh`（`admin/.env`에서 커넥션 읽기, 기본 컨테이너 내 mysqldump）, 매일 crontab 전체 백업, 기본 7일 보관（`--keep-days=30` 설정 가능）; 복구 훈련 절차와 RPO/RTO 설명은 OPS_RUNBOOK §1과 RECOVERY_RUNBOOK 참조.
- **모니터링 알림**: Prometheus + Grafana + `deploy/monitoring/alerts.yml`, AppDown / MysqlDown / RedisDown / ElasticsearchDown / QueueBacklog 커버, OPS_RUNBOOK §3 참조.
- **로그 로테이션**: 컨테이너 로그 `max-size 10m`, 호스트 로그 logrotate 매일 로테이션 30일 보관, OPS_RUNBOOK §4 참조.
- **애플리케이션 계층**: webman 다중 프로세스 상주, 큐 작업으로 시간 소요 작업 분리, `/health` 헬스 체크.

결론: 위 완화는 "장애 복구 가능"을 커버하며, **"장애 무중단"은 커버하지 않음**. 업무가 중단을 수용할 수 없으면 §3의 수평 확장에 진입해야 합니다.

## 3. 수평 확장 경로（우선순위 순）

확장 총칙: 먼저 종적（CPU/메모리/디스크 추가）후 횡적（컴포넌트 분리）, 먼저 미들웨어 후 애플리케이션, 각 단계는 독립 롤백 가능.

### 3.1 MySQL 마스터-슬레이브 + 반동기（1순위）

- 아키텍처: 마스터（기존 인스턴스）→ 슬레이브（새 머신）, 반동기 복제 활성화（`rpl_semi_sync_master_enabled=1`）.
- 읽기 확장: 애플리케이션이 마스터-슬레이브 분리 설정（`config/database.php`가 읽기/쓰기 분리를 지원하면 활성화; 아니면 먼저 마스터-슬레이브 HA만）.
- 백업 마이그레이션: 백업 스크립트를 슬레이브로 전환, 백업이 마스터를 압박하지 않게.
- 버전: 슬레이브는 마스터와 메이저 버전 일치 필요（현재 8.0.36）.
- 업그레이드 조건: 마스터 CPU 지속 >70%, 커넥션 수가 max_connections에 근접, 슬로우 쿼리 로그에서 스캔 행 수 급증.

### 3.2 Redis 센티널 또는 클러스터（2순위）

- 센티널（3노드）: 용량 요구가 높지 않을 때 센티널 선택, 전환 초 단위, 클라이언트가 `sentinel` 모드 지원 필요.
- Cluster（≥3마스터 3슬레이브）: 캐시량 > 단일 머신 메모리, 또는 쓰기 동시성이 높아질 때 Cluster 선택.
- 주의: 큐와 분산 락이 Redis에 의존하므로, 토폴로지 전환 시 `config/redis.php`를 함께 수정하고 장애 조치 상황에서 락/큐 동작 검증 필요.

### 3.3 Elasticsearch 독립 노드

- 단일 노드 ES는 복제본 없음, 인덱스 손상 시 검색 사용 불가. 최소한 독립 머신 + 복제본 1개로 마이그레이션.
- 데이터량 증가 후 인덱스 분할（비즈니스 도메인별）, 필요 없는 인덱스 복제본 비활성화로 리소스 통제.
- 업그레이드 조건: 힙 메모리 사용 >70% 지속, 쓰기 거부（`es_rejected_executions` 상승）, 쿼리 P95 1초 초과.

### 3.4 애플리케이션 다중 복제본 + 로드 밸런싱（마지막）

- admin/service 각각 2+ 복제본, 앞에 nginx 로드 밸런싱（라운드 로빈 또는 least_conn）.
- 선행 조건: 무상태（session은 Redis에, 로컬 파일 쓰기 의존 없음; 본 시스템은 JWT + Redis session, 기본 충족）.
- 이후 복제본 수만큼 처리 능력 배가 후, §3.1-3.3의 미들웨어 병목으로 복귀.

## 4. 데이터량 증가 트리거 포인트와 제안

| 트리거 포인트 | 임계값 제안 | 필수 조치 |
|--------|----------|----------|
| DB 총량 | > 50GB 또는 단일 테이블 > 5000만 행 | 마스터-슬레이브 분리 + 이력 청구서/로그 테이블 아카이브 |
| 슬로우 쿼리 | 일평균 슬로우 쿼리 > 10건 또는 단건 > 2s | 인덱스 추가, 테이블 분할, N+1 점검 |
| MySQL 커넥션 | 지속 > 80% max_connections | 커넥션 풀 + 마스터-슬레이브 |
| Redis 메모리 | > 70% + 지속 증가 | 만료 키 정리 → 센티널 → Cluster |
| ES 힙 메모리 | > 70% 또는 쓰기 거부 | 독립 노드 + 복제본 + 인덱스 분할 |
| CPU | 단일 코어 지속 > 80% + 큐 적체 | 애플리케이션 다중 복제본 → 미들웨어 분리 |
| 디스크 | > 80% | 백업/로그 정리, 콜드 데이터 아카이브 |

제안: 매월 위 표 1회 대조（데이터는 Grafana 패널에서 확보 가능）, 어느 항목이든 연속 2주 임계 초과 시 해당 확장 시작.

## 5. 확장 훈련 제안

- **분기 1회**: 복구 훈련（OPS_RUNBOOK §1.3 참조）, RPO/RTO 달성 검증.
- **연 1회**: 마스터-슬레이브 전환 훈련（새 머신에서 훈련, 프로덕션 마스터 건드리지 않음）: 슬레이브 구축 → 따라잡기 → 전환 → 양측 읽기/쓰기 검증 → 되돌리기.
- **첫 확장 후**: `scripts/loadtest`로 3개 경로（로그인/목록/검색）부하 테스트해 P95 달성 확인（`docs/PERFORMANCE_REPORT_2026-08-16.md` 참조）.
- **훈련 기록**: 훈련마다 변경 로그（CHANGELOG.md）에 기록: 시간, 훈련 항목, 결과, 잔여 문제 포함.

## 6. 업그레이드 경로 빠른 참조

```
단일 머신（현황）
  ├─ MySQL 마스터-슬레이브 반동기 ← 1순위
  ├─ Redis 센티널/Cluster ← 2순위
  ├─ ES 독립 노드+복제본 ← 3순위
  └─ 애플리케이션 다중 복제본+LB ← 마지막
        ↓
다중 머신 배포（단일 지점 없음, 장애 중단 수용 가능 → 분 단위 중단 수용 → 초 단위 전환）
```

> 현재 업무량에서는 확장 불필요, 본 문서는 "데이터량/장애 요구가 변할 때" 바로 따라 실행하기 위한 것으로, 임시 판단을 피하기 위함.
