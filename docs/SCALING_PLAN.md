# 扩容预案 (Scaling Plan)

> Copyright (c) 2026 erik <erik@erik.xyz> — https://erik.xyz

当前部署为单机 docker-compose（MySQL/Redis/Elasticsearch 与应用同机，见 `admin/docker-compose.yml`），无 HA。本文档说明风险与现有缓解，给出水平扩容路径、数据量触发点与演练建议。运维基线（备份/恢复、监控告警、日志轮转）见 [OPS_RUNBOOK.md](OPS_RUNBOOK.md)。

---

## 1. 当前部署与风险

### 1.1 现状

| 组件 | 版本 | 说明 |
|------|------|------|
| MySQL | 8.0.36 | 单实例，数据持久化在宿主机 volume |
| Redis | 7.2-alpine | 单实例，缓存/队列/锁 |
| Elasticsearch | 8.12.0 | 单节点，scout 全文检索 |
| nginx + webman | — | admin（8787）与 service（8788）同机多进程 |
| Prometheus + Grafana | — | 监控告警，同机 |

### 1.2 风险清单

| 风险 | 影响 | 概率 | 后果 |
|------|------|------|------|
| 单点故障（任一中间件宕机） | 全站不可用 | 低 | 高 |
| 宿主机磁盘/内存/CPU 争抢 | 慢查询、ES 卡顿、OOM | 中（数据增长后升高） | 中 |
| MySQL 单实例不可恢复损坏 | 数据丢失 | 极低 | 极高 |
| 无灾备机房 | 机房级故障全损 | 极低 | 极高 |
| 备份/恢复未演练 | 恢复超时或失败 | 中 | 高 |

## 2. 现有缓解（已落地）

- **备份**：单入口备份脚本 `scripts/backup.sh`（从 `admin/.env` 读连接，默认容器内 mysqldump），每日 crontab 全量备份、默认保留 7 天（`--keep-days=30` 可配置）；恢复演练流程与 RPO/RTO 说明见 OPS_RUNBOOK §1 与 RECOVERY_RUNBOOK。
- **监控告警**：Prometheus + Grafana + `deploy/monitoring/alerts.yml`，覆盖 AppDown / MysqlDown / RedisDown / ElasticsearchDown / QueueBacklog，见 OPS_RUNBOOK §3。
- **日志轮转**：容器日志 `max-size 10m`，宿主机日志 logrotate 每日轮转保留 30 天，见 OPS_RUNBOOK §4。
- **应用层**：webman 多进程常驻、队列任务解耦耗时操作、`/health` 健康检查。

结论：上述缓解覆盖"故障可恢复"，**不覆盖"故障不中断"**。业务不可接受中断时，需进入 §3 的水平扩容。

## 3. 水平扩容路径（按优先级）

扩容总原则：先纵向（加 CPU/内存/磁盘）后横向（拆组件），先中间件后应用，每一步可独立回滚。

### 3.1 MySQL 主从 + 半同步（第一优先）

- 架构：主库（现有实例）→ 从库（新机器），开启半同步复制（`rpl_semi_sync_master_enabled=1`）。
- 读扩展：应用配置主从分离（`config/database.php` 支持读写分离时启用；否则先只做主从高可用）。
- 备份迁移：备份脚本改指从库，避免备份压主库。
- 版本：从库需与主库大版本一致（当前 8.0.36）。
- 升级条件：主库 CPU 持续 >70%、连接数接近 max_connections、慢查询日志中扫描行数激增。

### 3.2 Redis 哨兵或集群（第二优先）

- 哨兵（3 节点）：容量需求不高时选哨兵，切换秒级，客户端需支持 `sentinel` 模式。
- Cluster（≥3 主 3 从）：缓存量 > 单机内存、或写并发升高时选 Cluster。
- 注意：队列与分布式锁依赖 Redis，切换拓扑时需同步改 `config/redis.php` 并验证锁/队列在故障转移下的行为。

### 3.3 Elasticsearch 独立节点

- 单节点 ES 无副本，索引损坏即检索不可用。至少迁移到独立机器 + 1 副本。
- 数据量增长后按索引拆分（按业务域），关闭不需要的索引副本以控资源。
- 升级条件：堆内存使用 >70% 持续、写入拒绝（`es_rejected_executions` 升高）、查询 P95 超 1s。

### 3.4 应用多副本 + 负载均衡（最后）

- admin/service 各起 2+ 副本，前置 nginx 负载均衡（轮询或 least_conn）。
- 前置条件：无状态（session 在 Redis、无本地文件写入依赖；本系统 JWT + Redis session，基本满足）。
- 之后按副本数翻倍处理能力，再回到 §3.1-3.3 的中间件瓶颈。

## 4. 数据量增长触发点与建议

| 触发点 | 阈值建议 | 必须动作 |
|--------|----------|----------|
| 数据库总量 | > 50GB 或单表 > 5000 万行 | 主从拆分 + 归档历史账单/日志表 |
| 慢查询 | 日均慢查询 > 10 条或单条 > 2s | 加索引、分表、检查 N+1 |
| MySQL 连接 | 持续 > 80% max_connections | 连接池 + 主从 |
| Redis 内存 | > 70% 且持续增长 | 清理过期键 → 哨兵 → Cluster |
| ES 堆内存 | > 70% 或写入拒绝 | 独立节点 + 副本 + 索引拆分 |
| CPU | 单核持续 > 80% 且队列堆积 | 应用多副本 → 中间件拆分 |
| 磁盘 | > 80% | 清理备份/日志，归档冷数据 |

建议：每月核对一次上表（数据可来自 Grafana 面板），任一项连续两周超阈值即启动对应扩容。

## 5. 扩容演练建议

- **每季度一次**：恢复演练（见 OPS_RUNBOOK §1.3），验证 RPO/RTO 达标。
- **每年一次**：主从切换演练（新机器上演练，勿动生产主库）：建从库 → 追平 → 切换 → 验证两端读写 → 回切。
- **首次扩容后**：用 `scripts/loadtest` 压测三路径（登录/列表/搜索）确认 P95 达标（参考 `docs/PERFORMANCE_REPORT_2026-08-16.md`）。
- **演练记录**：每次演练记入变更日志（CHANGELOG.md），包括：时间、演练项、结果、遗留问题。

## 6. 升级路径速查

```
单机（现状）
  ├─ MySQL 主从半同步      ← 第一优先
  ├─ Redis 哨兵/Cluster    ← 第二优先
  ├─ ES 独立节点+副本       ← 第三优先
  └─ 应用多副本+LB          ← 最后
        ↓
多机部署（无单点，可接受故障中断 → 可接受分钟级中断 → 秒级切换）
```

> 当前业务量下无需扩容，本文档用于"数据量/故障要求变化时"直接照做，避免临场决策。
